不談特定語言、不談技巧。這篇要回答的是：一份好維護的程式碼，到底在顧哪些事？這些事從 C 的年代到 Go、Rust，是怎麼一路被發現、被做過頭、又被修正回來的？

先講結論：好程式碼只在追求一件事

局部推理（local reasoning）：我只看眼前這一小塊，就能確定它對不對、改了會影響誰。

理由很樸素。程式碼被讀的次數遠多於被寫的次數，而人腦一次只裝得下很少的東西。系統小的時候，整個系統都在你腦子裡，怎麼寫都行；系統一旦大過一個人的腦容量，唯一還能安全修改它的方法，就是讓每一塊都能單獨被理解。

所以「好維護」不是乾淨、不是短、不是用了哪個模式，而是：

  • 要理解這一塊，不必先讀完其他地方。
  • 改一個決定，受影響的範圍和這個決定的大小相稱。
  • 不該發生的事，是結構上做不到，而不是靠大家記得不要做。

後面講的每一個面向，都只是「局部推理會被什麼東西破壞」的不同答案：到處都能改的狀態、說不清誰負責的決定、綁錯的抽象、漏進來的外部資料、看不見的失敗、沒人管的時間差。

五十年的演進：每一代都拿走一個自由

程式語言的歷史常被講成「功能越來越多」。換個角度看更準確：每一次重要的進步，都是拿走程式設計師的一種自由，因為那種自由讓人無法局部推理。

C 的哲學是信任程式設計師：給你一切能力，不擋你做任何事。這讓它快而自由，也讓正確性完全壓在人的記憶上。之後每一代，都是對某一種「靠人記得」的反動：

思潮 它反對什麼 留下來的 做過頭的地方
結構化程式設計 goto 讓流程無法追蹤 函式、迴圈、區塊：控制流程可以由上往下讀 幾乎沒有，這是最乾淨的一次勝利
模組化、資訊隱藏 任何地方都能碰任何資料 把「容易變的決定」藏在介面後面 無
物件導向 資料和操作它的規則分家 封裝、介面、多型 繼承被當成重用工具，長出很深的類別樹；什麼都要是類別；為模式而模式
垃圾回收 手動管理記憶體必然出錯 記憶體安全成為預設 記憶體之外的資源（檔案、連線、鎖）反而沒人管了；生命週期變得隱形
受檢例外（Java） 失敗被默默忽略 「失敗應該出現在函式簽名裡」這個想法 形式太笨重，逼得人寫空的 catch，反而製造了它想消滅的東西
動態語言 型別宣告的繁文縟節 快速試驗、簡潔的語法 大型專案改不動，於是型別標註又被加回來
函數式 可變的共享狀態 預設不可變、純函式、把資料當值 追求全面純粹時，抽象層疊到常人讀不懂
Go C++ 與 Java 的複雜度 小語言、組合取代繼承、錯誤是普通的回傳值、統一的格式 為了簡單長期不提供泛型，逼出大量重複與繞路，2022 年才補上
Rust 「安全」和「效能」只能二選一 擁有權寫進型別、沒有 null、不安全的部分要明確標示 學習成本高；簡單的事有時也得和編譯器周旋

從這段歷史可以讀出三件事。

第一，進步多半是限制，不是能力。 拿掉 goto，你才能相信一個區塊只有一個入口；拿掉任意修改，你才能相信一個值不會在背後變掉。好的限制是一種保證。

第二，好想法常常先以過頭的形式出現，留下來的是想法，不是形式。 「失敗應該看得見」這個想法從沒死過，只是換了三次外形：

textJava (1996)   void save(Order o) throws IOException          // 受檢例外：想法對，太笨重
Go   (2009)   func Save(o Order) error                       // 錯誤是回傳值：簡單，但可以不檢查
Rust (2015)   fn save(o: &Order) -> Result<(), io::Error>    // 結果型別：不處理就編譯不過

繼承也是：類別樹被放棄了，但「依賴介面而不是實作」被保留下來，Go 和 Rust 都只留介面與組合。動態語言也是：自由被保留，但型別以「可選」的形式回來。

第三，判斷一個限制值不值得，只看一件事：它換來的保證，抵不抵得過它的成本。 矯枉過正的共同點，都是成本超過了保證：為了重用而繼承、為了彈性而分層、為了純粹而抽象、為了簡單而拒絕必要的工具。

語言會替你守住其中幾項，但沒有語言守得住全部。下面這些面向，不管用什麼語言都得自己顧。

十一個要顧的面向

1. 狀態：會變的東西越少越好

程式難懂，幾乎都是因為狀態：一個值現在是什麼，取決於之前發生過的所有事。每多一個可變的欄位，要考慮的可能性就翻倍。

  • 能不存就不存。算得出來的值不要另存一份，兩份遲早對不上。
  • 預設不可變。會變的東西要有理由，而且範圍越小越好。
  • 讓不合法的狀態寫不出來，而不是寫出來再驗證。
typescripttype Order =
  | { status: "pending" }
  | { status: "paid"; paymentId: string }
  | { status: "cancelled" }
  | { status: "refunded"; paymentId: string; refundId: string };

這條線索貫穿整段歷史：null 被發明者自己稱為「十億美元的錯誤」，後來的語言都把「可能沒有值」變成型別的一部分；函數式語言把不可變當預設；Rust 規定同一時間「可以多人讀」或「只有一人寫」，不能兩者並存。

做過頭的樣子：為了不可變而到處複製大型資料；為了型別完美，把業務上本來就模糊的東西硬塞進僵硬的模型。

2. 責任與擁有權：每件事只有一個主人

責任是對決定而言：這條規則由誰判斷？原則是把責任交給擁有做這件事所需資訊的那一方。訂單能不能退款，該由訂單決定，而不是散在每個呼叫它的地方各寫一個 if。

一個很有用的區分：能讀的人可以很多，能決定的只能有一個。

typescriptaccount.isSuspended();          // 到處都能問
accountPolicy.suspend(account); // 只有一個地方能做，驗證與稽核都在這裡

放大到系統之間也一樣。三個系統各存一份客戶狀態不是問題，問題是三個都自認說了算。資料可以複製，決定權不能複製。

擁有權是對資源而言：這塊記憶體、這個檔案、這條連線、這個背景工作，誰負責結束它？C 把這件事交給記憶；垃圾回收解決了記憶體，卻讓其他資源的主人變得模糊；Rust 把擁有權寫進型別，讓編譯器檢查。不管語言幫不幫你，問題都在：每一個被建立的東西，都要說得出誰負責收掉它，包括請求結束後還在跑的背景工作。

另一個常用的切法是把**「決定」和「動手」分開**：判斷該做什麼的邏輯不碰外部世界，執行的部分只負責把決定變成效果。這樣規則可以單獨測試，出事時也分得清是判斷錯了，還是做到一半掛了。

做過頭的樣子：責任切得太碎，一條流程要跳過十個只有兩行的物件才拼得起來。單一責任量的是「改變的理由」，不是行數；一段三十行、完整呈現一條流程的函式，比九個互相呼叫的小函式更容易理解。

3. 抽象：只合併會一起變的東西

抽象的本質是一個賭注：我賭這幾樣東西未來會為了同樣的理由一起改變。賭對了，改一處就好；賭錯了，原本不相干的東西被綁在一起，改這個會壞那個。

最常見的錯是把「長得像」當成「是同一件事」：

typescript// 當初：兩種取消流程看起來一樣，合併
cancelSubscription(sub);

// 半年後：一種要退款、一種要挽留、生效時間也不同
cancelSubscription(sub, { refund: true, retainAccess: false, immediate: false });

函式長出一堆開關，就是當初賭錯了的訊號。它不再表達一個概念，而是在協調幾個碰巧長得像的概念。

所以：

  • 「不要重複」指的是同一份知識不要有兩個版本，不是相似的字不能出現兩次。
  • 重複是看得見的債，錯的抽象是看不見的耦合。前者一眼就看到，後者要等改壞了才知道。沒把握時，先讓它重複。
  • 只保護有證據會變的地方。「外部服務的介面會自己改」是看得見的證據，值得包一層；「未來可能要支援五種資料庫」通常只是想像。
  • 每一層都要說得出它保護什麼。把它拿掉，如果只是少了幾個轉呼叫的方法，它就是儀式。

做過頭的樣子：物件導向全盛期的過度設計。只有一種實作，卻先寫了工廠、策略、註冊表；每一層都只是把參數原封不動往下傳。整齊的複雜度還是複雜度。

4. 邊界：中間要無聊，兩邊要多疑

邊界是信任等級改變的地方。邊界之外的東西你控制不了：格式會變、欄位會缺、同一個意思有三種寫法。邊界之內，你應該可以放心。

  • 在入口解析一次，轉成自己定義的型別，之後內部不必再到處檢查。到處都在去空白、判空值、猜狀態的程式碼，就是邊界沒守住，外面的不確定性漏進了裡面。
  • 用自己的語言，不用別人的。外部服務的狀態名稱一旦散落在業務邏輯裡，你的系統就開始用它的世界觀思考，換一家就得重寫規則。
  • 翻譯不是改名。兩個來源都叫「成功」，一個指已授權、一個指已入帳，把它們當成同一個值就是錯的。
  • 不認得就說不認得。「不是失敗」不等於「成功」；查不到就當成零，是沒有人做過的決定。
typescripttype PaymentState = "authorized" | "settled" | "failed" | "unknown";

function fromProvider(raw: unknown): PaymentState {
  switch (raw) {
    case "succeeded":       return "settled";
    case "requires_action": return "authorized";
    case "canceled":        return "failed";
    default:                return "unknown"; // 不猜
  }
}

Rust 的 unsafe 是同一個想法用在語言層級：危險的事可以做，但必須圈在一個標了記號的範圍裡，出事時知道去哪裡找。

做過頭的樣子：每兩個模組之間都築一道牆、每筆資料跨一層就轉換一次型別。邊界只該出現在信任等級或變動節奏真的不同的地方。

5. 依賴方向：讓善變的依賴穩定的

「誰知道誰」決定了改動會往哪裡擴散。A 依賴 B，B 一改 A 就可能要跟著改。所以原則是：依賴要指向比較穩定的那一方。

  • 核心的業務規則最穩定，應該誰都不依賴；畫面、資料庫、外部服務最善變，應該由它們來依賴核心定義的介面，而不是反過來。
  • 隱藏的依賴最危險：全域變數、目前時間、環境設定、單例。函式簽名上看不出它需要這些，卻少了就不能跑、換了就行為不同。能用參數傳進來的就傳進來。
  • 組合優於繼承。繼承是最強的一種依賴：子類別綁死在父類別的每一個實作細節上。這是物件導向留下的最大教訓，Go 和 Rust 乾脆不提供類別繼承。

做過頭的樣子：為了「反轉依賴」，每個類別都配一個只有一種實作的介面，再加上一套把所有東西自動接起來的框架，結果沒有人看得出執行時到底是誰在呼叫誰。

6. 失敗：它是功能的一部分

只描述順利情況的程式碼，只寫了一半。失敗不是功能外圍的清理工作，而是功能本身的行為。

  • 失敗要看得見。這是從受檢例外到錯誤回傳值、再到結果型別一路沒變的想法：一個函式會不會失敗，應該寫在它的簽名上，而不是藏在文件裡。
  • 不要吞掉錯誤。空的錯誤處理、只記一行日誌就繼續，都是讓後面的程式以為這一步成功了。
  • 不確定時停下來，不要猜。當機會被發現、被修好；猜錯的結果會安靜地錯上好幾個月。
  • 結果有三種：成功、失敗、不知道。跨出自己的程序之後，「沒收到成功」不等於「失敗」。把「不知道」當成一個正式的狀態來處理，而不是硬歸到其中一邊。
  • 預期內的失敗和程式錯誤是兩回事。使用者名稱被用掉、卡片被拒，是業務的正常結果，用回傳值表達；真正沒料到的才是例外。混在一起，警報就會被雜訊淹沒。
  • 能處理的人才處理。每一層都攔下來再往上丟，只會讓同一個錯誤出現三次。這一層既不能復原、也不能補充資訊，就讓它過去。
  • 防不住的要能修。再好的預防都會輸給現實，所以要有辦法發現系統已經不一致，並把它修回來。復原是功能，不是緊急程序。

做過頭的樣子：每一行都包一層防禦、每個值都再檢查一次。這通常代表邊界沒守好，或是狀態模型允許了不該存在的組合；該修的是上游，不是在下游加更多檢查。

7. 時間：兩個動作之間，世界會變

一行一行往下讀的程式碼，暗示著一個單純的世界：這行做完才做下一行，中間什麼都不會發生。只要有並行、網路或背景工作，這個假設就不成立。

typescriptif (!(await userExists(email))) await createUser(email);
// 兩個請求同時進來，各自都查到「不存在」，各自都建立了

兩邊各自都做了正確的判斷，合起來卻破壞了規則。問題不在任何一行，而在兩行之間的空隙。

時間帶來的四個問題，每一個都對應一個被打破的假設：

假設 現實 該有的保護
這件事只會發生一次 重試、重複送達、使用者連點兩下 重做一次的結果和做一次相同
這幾步要嘛全成功、要嘛全失敗 做到一半中斷 清楚知道「不可分割」的範圍到哪裡為止，超出的部分要能補救
我讀到之後、寫入之前，沒人改過 別人剛好改了 寫入時確認資料還是我讀到的那個版本
晚點再處理，總會處理完 進來的比處理的快 容量有限時要能拒絕，而不是無限排隊

Go 的口號「不要用共享記憶體來溝通，要用溝通來共享記憶體」和 Rust 在編譯期禁止資料競爭，都是對同一個問題的回答：共享、可變、並行，三者不能同時存在，至少要放棄一個。

做過頭的樣子：在單機、單人使用的小工具上套用分散式系統的全套機制。保護要跟著真實存在的風險走。

8. 明確與隱含：重要的事要看得見

這是語言史上擺盪最多次的一條軸。太明確，重點被淹沒在樣板裡；太隱含，沒有人知道實際上發生了什麼。

兩邊都有代價：

  • 隱含的代價是驚訝。看不見的型別轉換、自動注入的依賴、靠命名規則觸發的行為、會偷偷改動參數的函式。寫的時候很省事，除錯時要先知道一堆「你應該要知道」的事。
  • 明確的代價是雜訊。每一步都寫出來，真正重要的那個決定反而不顯眼。

判準不是「越明確越好」，而是：重要的決定要看得見，無關緊要的細節才可以藏。

  • 會改變外部世界的動作（扣款、送出訊息、寫入資料庫）不該藏在一個名字很無害的函式裡。
  • 三個重要的業務分支，直接寫出來讓人一眼看到，勝過藏在一張要去別處找的對照表裡。
  • 來自程式碼之外的理由（外部服務的限制、被否決過的做法、一次事故的教訓）寫成註解。重述程式碼的註解是雜訊，但「為什麼」只有註解留得住。
  • 命名是最便宜的明確：名字取對了，就不需要另外解釋。

Go 是這條軸上「偏明確」的代表：沒有例外、沒有隱式轉換、錯誤一定要寫出來處理，連排版都只有一種。它換來的是任何人打開任何一份程式碼都看得懂，付出的是比較囉嗦。

做過頭的樣子：兩端都有。一端是「魔法」框架，寫三行就能動，壞掉時沒人知道為什麼；另一端是儀式性的樣板，每個欄位都手寫一遍存取方法。

9. 簡單：分清楚哪些複雜是你加的

複雜度有兩種。本質的來自問題本身：付款就是會有「不知道成功了沒」的時候，你躲不掉。附加的來自解法：多出來的層、為了想像中的需求留的擴充點、不必要的工具。好的設計不是消滅複雜度，而是不替問題增加它本來沒有的複雜度，並且把躲不掉的部分關在少數幾個地方。

要注意「簡單」和「容易」不是同一件事：

  • 簡單是指東西之間沒有糾纏，可以分開來理解。
  • 容易是指順手、熟悉、現在打起來快。

容易的做法常常不簡單（一個什麼都包的全域物件用起來很順手），簡單的做法一開始常常不容易。

另一個方向的錯也一樣常見：假裝問題比實際簡單。把三種結果壓成成功與失敗兩種，程式碼變短了，複雜度並沒有消失，只是搬到了半夜的事故裡。

做過頭的樣子：把「簡單」當成拒絕一切工具的理由，結果用大量重複和手工繞路，去補一個本來該有的抽象。

10. 可驗證：把假設交給機器記

每個系統都靠假設運作：這個欄位不會重複、這個函式只會在交易裡被呼叫、訊息可能會重複送達。問題不在於有假設，而在於假設只存在某個人的腦子裡。

同一個假設，放的位置不同，保護力差很多：

放在哪裡 誰會碰到它
某個人的記憶 只有他，而且他會離職
註解、文件 剛好讀到的人
測試 改壞它的人，在合併之前
程式裡的檢查 走到這條路徑的每一次執行
型別 所有編譯得過的程式碼
資料庫約束 所有寫入，包括並行的、和未來才寫的

原則是：越重要的假設，放在越下面。前面那個「先查再寫」的例子，應用程式的檢查可以留著給使用者友善的訊息，但真正守住唯一性的必須是資料庫。

這也是整段語言史的方向：把更多「靠人記得」的事，變成「機器會檢查」的事。型別系統、擁有權檢查、統一的格式工具，都是同一個想法。

另外兩點：

  • 難測試是設計的訊號。一段邏輯要先架好資料庫和五個假物件才能測，通常代表決定和動手纏在一起了。
  • 執行時也要留下證據。出事時能不能從紀錄重建「當時發生了什麼」，取決於程式有沒有把重要的決定和狀態轉換記下來。

做過頭的樣子：追求覆蓋率數字，寫了一堆只是把實作再抄一遍的測試，一重構就全壞，卻抓不到真正的錯。

11. 演進：為「改得回來」而設計

程式碼被維護的時間遠長於被撰寫的時間，而需求一定會變。所以設計的對象不只是現在的功能，還有未來的修改。

  • 決定有貴有便宜，注意力要照著分配。改一個私有函式的名字是下午的事；公開的介面、存下來的資料格式、被別人依賴的行為，一旦放出去就很難收回。前者快快做，後者慢慢想。
  • 看影響範圍。一個小需求如果要動十五個地方，問題不在需求，而在某個概念已經漏得到處都是。
  • 只要有夠多人在用，任何看得見的行為都會有人依賴，不管你有沒有承諾過。所以對外露出的東西越少越好。
  • 好刪比好擴充重要。容易整塊拿掉的程式碼，代表它和別人的糾纏很少；這比預留十個擴充點更能應付未知的未來。
  • 系統的邊界會長得像團隊的邊界。一個模組沒有明確的負責人，最後就沒有人敢改它。

做過頭的樣子：為了永遠不破壞相容性，把每一個歷史包袱都背在身上；或是反過來，為了未來所有可能的變化預先設計，讓今天的系統背著永遠不會來的需求。

GRASP 與 SOLID 放在哪裡

這兩套常見的物件導向原則，在上面的地圖裡各有位置。看了就知道它們主要涵蓋第 2、3、5 項，對狀態、失敗、時間幾乎沒有著墨，所以不能只靠它們：

原則 一句話 屬於哪個面向
資訊專家（GRASP） 有資訊的人負責 責任
創造者（GRASP） 誰建立，誰保證它一出生就合法 責任、狀態
控制器（GRASP） 流程協調要有固定的家 責任
高內聚、單一責任（SRP） 一個模組只有一個改變的理由 責任、抽象
低耦合（GRASP） 改這裡不必改那裡 依賴方向
多型（GRASP） 依型別變化的行為交給型別 抽象
防護變異（GRASP）、開放封閉（OCP） 把會變的點包在穩定的介面後面 抽象、演進
間接、純虛構（GRASP） 用中介物件把兩邊隔開 邊界
里氏替換（LSP） 能互相替換的才算同一種 抽象、邊界
介面隔離（ISP） 不要逼使用者認識用不到的東西 依賴方向
依賴反轉（DIP） 核心定義需求，外部去配合 依賴方向

最後：原則之間會打架

這些面向不是一張可以全部打勾的清單，它們會互相衝突：

  • 消除重複，會增加耦合。
  • 寫得明確，會增加雜訊。
  • 加上保護，會增加複雜度。
  • 保留彈性，會犧牲簡單。

所以每一條原則都要回到三個問題：它在防什麼？這裡真的有那個問題嗎？照做的代價是什麼？ 歷史上每一次矯枉過正，都是有人只記得規則的外形，忘了它原本要解決的問題。

真正的判斷只有一個尺度：這個決定錯了有多貴、多難反悔。便宜又好改的，選最簡單的做法；昂貴又難回頭的，才值得多花力氣去保護。

檢視一段設計時，可以依序問：

  1. 這裡有哪些東西會變？能不能更少？
  2. 這個決定的主人是誰？有沒有第二個地方也在做同樣的判斷？
  3. 這兩段相似的東西，會為了同一個理由一起改嗎？
  4. 外面的資料，是在哪裡變成我可以信任的？
  5. 核心邏輯有沒有依賴到比它善變的東西？
  6. 這一步之後如果中斷，系統知道什麼？
  7. 這兩個動作之間，如果有別人插進來會怎樣？
  8. 這裡最重要的決定，一眼看得出來嗎？
  9. 哪些複雜度是問題本身的，哪些是我加的？
  10. 我相信它是對的，憑的是機器的檢查，還是我的記憶？
  11. 這個決定如果錯了，改回來要付出什麼？
