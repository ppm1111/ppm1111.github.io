告警是怎麼被記下來的

這份教學只講一條路：「某件事超標了」到「alerts 表多一筆」之間發生的所有事。兩個入口（metrics 的內存門檻評估、security 代碼直接寫）匯進同一個出口（common 的 AlertRecorder），中間藏著滑動窗口、dedup、獨立交易這些機制。所有代碼都從 repo 現抄，路徑以純文字標注。建議先讀 metrics教學.html 的第 5、7 章（step 機制與 publish()），本文從那個切點直接接下去。

1全景：一條告警的一生

整個告警系統的設計哲學是：alerts 表是唯一的終點，寫進去就是「發出告警」。沒有通知推送、沒有外部服務——查這張表就是看告警。而通往這張表的路只有一條門（AlertRecorder），但門前有兩種來客：

決定理由
append-only，沒有「已處理」欄位這是事件紀錄，不是工單系統。追蹤處理狀態是另一個領域的事，混進來會讓寫入端背上更新的職責

3規則設定與啟動驗證

門檻規則全部寫在設定檔，一條規則唸出來就是一句話：「window 內，metric 的 sample 欄位做 agg 聚合，超過 above 就以 severity 告警」。

每個欄位對應 AlertRulesProperties.Rule 這個 record 的一個參數，而驗證就寫在 record 的 compact constructor 裡——設定錯了，app 直接起不來，而不是跑到半夜才發現某條規則沒生效：

欄位意義預設
name規則名稱（全域唯一，外層建構子檢查重複）；寫入 alerts 時 alert_type = metrics.<name>必填
metric + sample盯哪個指標的哪個欄位。gauge/counter 用 value；timer 拆出來的三筆用 count / sum / max（metrics教學.html 第 7 章）value
matchattributes 部分比對：series 的 tag 須包含這些 key/value。不寫 = 該指標所有 series 一起算全部
window + agg往回看多久、怎麼聚合。sum（沒資料視為 0）/ max / avgsum
above + severity超過就觸發，寫入的嚴重度severity 預設 WARNING
為什麼 server-errors 的門檻是 above: 0？因為 sample 是增量（step 體系），「5 分鐘窗口內 5xx 的 count 總和 > 0」就是「這 5 分鐘內發生過任何一次 5xx」。而 db-pool-pending 用 agg: max 是因為 pending 是 gauge（瞬時值）——「窗口內曾經有人排隊」要看最大值，加總一堆瞬時值沒有意義。agg 的選擇跟著指標的型別語義走。

4門檻規則的內存評估

門檻規則的評估不查 DB、不跑排程——它搭指標管線的便車。metrics教學.html 第 7 章講過，DatabaseMeterRegistry.publish() 每 10 秒在 metrics-store 執行緒上把這個 step 的增量轉成一批 MetricSample。寫完 DB 之後，同一批資料會再發給所有 StepListener：

兩段各自 try/catch 是刻意的錯誤隔離：DB 寫失敗不影響告警評估，告警評估炸了也不影響下一輪寫入。還有一個重要性質：告警看到的數字和 metrics_sample / UI 完全同一批——同一個切點、同一個 recordedAt。告警說超標，去 UI 一定畫得出那個尖峰，不會有「告警和圖表對不上」的靈異現象。

唯一的 StepListener 實作就是 ThresholdAlertEvaluator。它的 onStep() 對每條規則做兩件事：餵資料、做評估——第 2 章你問過的那兩個欄位（windows 是狀態、alertRecorder 是出口）就在這裡分工：

為什麼在內存評估，而不是像舊方案那樣排程查 DB？三個理由：① 規則數量不影響 SQL 負載——一百條規則也只是內存迴圈，DB 一句 SQL 都不多；② 零延遲——step 一結束立刻評估，不用等下一輪排程；③ 數字保證一致（上面說的同一批資料）。代價寫在類別的 javadoc 裡：重啟後窗口是空的，重啟後的第一個 window 期間「只會少算、不會誤報」——對告警來說是正確的取捨方向。

最後注意 record() 呼叫的最後一個參數 rule.window()——那是 dedup 的抑制間隔。持續超標時，告警不會每 10 秒寫一筆：同一條規則在一個 window 長度內只落一筆（第 7 章的 SQL 負責擋）。

5RuleWindow：滑動窗口

RuleWindow 是一條規則的「記憶」。規則要回答的是「過去 5 分鐘總共怎樣」，但每次 onStep 只拿得到最近 10 秒的增量——所以必須把格子留著。資料結構就是一個 ArrayDeque<Slot>：新 step 從尾端進，過期的從頭端出。

null 和 0 的區別是這個類最細膩的地方。窗口內完全沒資料時，aggregate() 回 null 而不是 0——因為對 avg 和 max 來說，「沒有資料」和「值是 0」是兩回事（平均 0 和沒量到是不同的事實）。只有 sum 的呼叫端（第 4 章的 evaluate()）會把 null 視為 0，因為增量的世界裡「沒有 sample = 沒有發生 = 0 次」。這套語義是刻意對齊舊 SQL 版 aggregate 的行為，搬進內存時不改變任何規則的觸發條件。
注意 javadoc 那句「非執行緒安全」。ArrayDeque 沒有任何鎖，敢這樣寫是因為整條鏈（publish → onStep → record/aggregate）都跑在同一條 metrics-store 執行緒上，天生串行。如果哪天有人在別的執行緒碰 RuleWindow，這個前提就破了——所以註解把前提寫死：「只在 registry 的 step 執行緒上使用」。

還有一個只在觸發時才做的動作：breakdown() 把窗口內各 series 的貢獻由大到小列出前 5 條，塞進告警的 detail。所以收到 slow-sql 告警時，detail 裡直接寫著是哪幾句 statement 貢獻了幾次慢查詢——不用再回 UI 翻。它遍歷每個 slot 留著的 entries，成本比 aggregate 高，但「只在觸發時呼叫，成本不在熱路徑上」（RuleWindow.java 82-84 行的註解）。

兩個入口最後都走進同一個方法。AlertRecorder 做的事是「把呼叫端不想管的脈絡補齊」：

三個「自動補」的欄位解釋了第 2 章表裡那些 nullable 欄位的來源：

  • client_ip：從當前 HTTP 請求拿。排程執行緒（門檻規則、看門狗）沒有請求上下文，拿到 null——所以「client_ip 有值」本身就代表「這筆告警是某個 API 請求觸發的」。
  • trace_id / request_id：直接撈 MDC。security 的告警發生在請求處理中，MDC 有值；metrics 的告警發生在 metrics-store 執行緒上，MDC 是空的——欄位的有無忠實反映了告警的出身。
  • 整個方法包在 try/catch 裡：告警寫失敗只記 warn。寧可丟一筆告警，不能讓「記告警」弄死正在處理的登入請求——告警永遠是旁路，不是主流程。

REQUIRES_NEW 的意義用 token reuse 的場景看最清楚：refresh 流程偵測到重用後會丟 UnauthorizedException，而撤銷 family 的寫入靠 noRollbackFor 保住——但告警不想賭在外層交易的 rollback 規則上。開一個全新的、立刻提交的交易，告警就和外層的命運徹底解耦：外層就算整個 rollback，alerts 表那筆也已經提交了。

為什麼不寫成兩步（先 SELECT 檢查、沒有再 INSERT）？因為兩步之間有競態窗口：兩條執行緒（或兩台機器）同時檢查、同時發現「沒有」、同時寫入 → 重複告警。INSERT ... SELECT ... WHERE NOT EXISTS 是單一 statement，檢查和寫入在同一個原子動作裡。這也是 MetricsAlertScheduler javadoc 說「多台部署每台都會跑，由 alerts 的 dedup_key 抑制重複寫入」的底氣——dedup 做在 DB，天然跨機器。查詢條件 (dedup_key, created_at) 正好踩在 idx_alerts_dedup 索引上，每次寫入的 dedup 檢查是 index scan，不掃表。

8看門狗：store-stalled

第 4 章的評估有一個盲點：它搭指標管線的便車，所以管線死了它跟著死——而且死得悄無聲息（沒有 step，就沒有評估，就沒有告警）。管線停擺意味著所有門檻規則同時失明，所以需要一條「監控監控本身」的旁路，而且它必須滿足一個條件：不能跑在它要監控的那條執行緒上。

它判斷的依據 MetricsWriteState 是一個最小化的共享狀態——一個 volatile Instant：每次 DatabaseMetricsStore 成功寫完 DB 就蓋一次時間戳（metrics教學.html 第 6 章那個 tracked-store lambda）。看門狗只讀內存，不查 DB——「管線活著嗎」這個問題不應該靠 DB 查詢回答，不然 DB 慢的時候看門狗自己也卡住。

注意這是整個告警系統裡唯一的 @Scheduled——門檻規則不用排程（跟著 step 走），只有看門狗用。而且它跑在 Spring 的排程執行緒池上，和 metrics-store 執行緒完全獨立：step 執行緒死了，排程執行緒才抓得到。如果把這個檢查也掛成 StepListener，它就和被監控者同生共死，永遠發不出「我死了」的告警。這就是 yml 裡 interval: 10s 的用途——它只控制看門狗的檢查頻率，跟門檻規則無關（第 3 章設定註解寫的「門檻規則跟著 step 走，不吃這個值」）。
兩個防誤報的細節：① MetricsWriteState 的初始值是啟動時間——app 剛起來還沒寫過第一筆，自帶一個 stalledAfter（2 分鐘）的緩衝，不會一開機就告警；② 告警的抑制間隔也是 stalledAfter——持續停擺時每 2 分鐘留一筆，既能看出「還沒好」，又不會灌爆 alerts 表。當然它有自己的極限：app 整個掛了，誰也寫不了告警——那是外部監控的事，javadoc 裡明說了。

730 天遠長於指標資料（raw 14 天、hourly 365 天），因為告警的價值密度不同：metrics_sample 一天幾十萬筆、多數永遠沒人看；alerts 一筆就是一次事件，安全稽核（「這個帳號歷史上被鎖過幾次」）需要看得夠遠。

整條管線的已知限制，也是讀完這份教學後你能準確說出「為什麻」的地方：

限制原因／邊界
沒有通知推送（email / Slack）範圍決定：不依賴外部服務。要看告警得主動查表。接通知時，入口不用動——在 AlertRecorder 之後加一個出口即可
重啟後窗口清空內存評估的代價。重啟後第一個 window 期間只會少算不會誤報；跨重啟的持續異常會由下一個 window 重新抓到
app 整個掛掉時無告警看門狗跑在 app 裡，app 死了誰也寫不了 DB。這層要靠外部監控（compose healthcheck / 人）
規則不能動態改規則是 @ConfigurationProperties，改了要重啟。換來的是啟動即驗證（第 3 章）：不存在「改壞了但沒人發現」的狀態
alert_type 沒有 registry字串約定（auth.* / metrics.*），新增類型不用改任何中心清單——代價是 typo 不會被抓到
全文回顧，一筆告警的欄位是這樣湊齊的：alert_type / severity / message / dedup_key / detail 由入口決定（門檻規則拼規則名和 breakdown，security 拼事件脈絡）；created_at / client_ip / trace_id / request_id 由 AlertRecorder 自動補；「這筆到底寫不寫」由那句 WHERE NOT EXISTS 決定；「這筆活多久」由 Retention 決定。每一層只管自己的事——這就是兩個入口能共用一個出口的原因。
