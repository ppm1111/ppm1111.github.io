user_system 實作教學

一個使用者系統（帳號、JWT 登入、RBAC），附帶自建的指標收集與告警，原則是不依賴外部服務：log 寫檔、指標進同一個 PostgreSQL、監控 UI 和告警都由 Spring Boot 自己提供。本文按模組分章，每章先講「為什麼這樣設計」，再給圖和真實代碼對照。技術棧：Java 25、Spring Boot 4、Maven 多模組、MyBatis、Liquibase、PostgreSQL、Redis。

1全景

整個系統只有四個容器：nginx、Spring Boot app、PostgreSQL、Redis。沒有 Prometheus、沒有 Grafana、沒有 ELK——指標、告警、監控頁面全部由 app 自己提供，資料就放在業務用的同一顆 PostgreSQL 裡。

小系統引入一套完整的可觀測性堆疊（Prometheus + Grafana + Alertmanager）要多維運三四個服務。這個專案選擇反向操作：app 每 10 秒把指標寫進自己的 DB，用一頁靜態 HTML 畫圖，告警規則在內存評估、觸發才寫一筆 alerts。代價是單機限制（見第 10 章結尾），換到的是部署面只剩 docker-compose 四個服務。

2共用地基（common）

所有 API 的回應長一個樣、所有例外走同一個出口、所有時間來自同一個來源——這三件事都在 common 模組，業務代碼因此不用自己處理「包裝回應」「接例外」「取時間」。

2.1 統一回應：CommonResponse

注意設計取捨：錯誤「種類」由 HTTP status code 表示，body 裡的 message 只是翻譯好的人話。客戶端判斷邏輯看狀態碼就夠，不用解析字串。分頁另有 PageCommonResponse，欄位是 total_count / total_page / page_num / page_count（全域 Jackson 設成 SNAKE_CASE）。

2.2 全域例外處理

自己從零寫 @ExceptionHandler 很容易把 Spring MVC 原生的語義弄丟——例如 405 要帶 Allow header、415 的狀態碼。所以 GlobalExceptionHandler 繼承 ResponseEntityExceptionHandler：Spring 自己的例外沿用 Spring 決定的狀態碼與 header，只把 body 換成 CommonResponse；自訂例外（BaseException 家族）才由例外自己決定狀態碼。
  • 4xx 記 WARN、5xx 記 ERROR + stack trace。意義在第 9 章會回收：只有真的沒預期到的例外才是 500，所以「5xx 告警」不會被亂打的請求觸發。
  • 驗證錯誤回 400，data 是 {欄位: 訊息}，欄位名轉 snake_case 跟回應格式一致。
  • 429 另外加 Retry-After header，配合 rate limit。

2.3 可測試的時間：TimeProvider

全專案取「現在」只有一個入口：TimeProvider.now()（回 UTC Instant）。它和 Spring 的 Clock bean 共用同一個時間來源，測試時注入 Clock.fixed(...) 就能把整個系統的時間釘死——後面章節的登入鎖定、refresh 過期、指標窗口、保留期清理，測試全靠這招寫成純單元測試。

設定類也有一個共同慣例：全部是 record + @ConfigurationProperties，在 compact constructor 裡驗證，設定不合法時啟動直接失敗（fail fast），而不是跑到一半才發現門檻是負數。

3看得見的系統：log 與追蹤

出問題時要能回答三個問題：這個請求做了什麼？跑了哪些 SQL？是誰發的？答案是三個 log 檔加 MDC 關聯：

檔案logger內容
logs/app.log一般應用程式 log
logs/request.logapp.request每個請求：method、path、status、耗時、IP、user_id、UA
logs/sql.logapp.sql每筆 SQL：statement、耗時、筆數、SQL、參數（敏感參數遮成 ***）

每一行都帶 traceId / spanId / request_id / user_id（MDC），拿任何一行的 traceId 就能把三個檔案裡同一個請求的紀錄全撈出來。app.request 和 app.sql 設 additivity=false，不會重複寫進 app.log。

3.2 SQL 計時：MyBatis Interceptor

SqlLogInterceptor 攔截 MyBatis Executor 的 update / query，一個攔截點同時餵三個出口：app.sql timer 指標、超過門檻再記 app.sql.slow counter、以及 sql.log。

  • finally 計時：SQL 丟例外也要算一筆，不然最慢的（逾時的）反而沒紀錄。
  • tag 用 statement id 不用 SQL 全文：SecurityUserMapper.findById 這種短名，tag 基數有限，指標才不會爆炸。
  • 參數名含 password / secret / hash 或以 token 結尾的值寫 log 前遮成 ***。
  • 它在 common 模組，用 @ConditionalOnClass 偵測到 MyBatis 才註冊——common 不強迫每個專案都用 MyBatis。

5登入與雙 token

認證用兩種 token，角色完全不同：

Access tokenRefresh token
形式JWT（HS256），自含 sub=userId、ver=token_version、jti、iss、exp隨機 32 bytes 的不透明字串
有效期15 分鐘14 天
伺服器端儲存不存（無狀態驗證）DB 只存 SHA-256 雜湊
用途每個 API 請求換發新的 access + refresh（每用一次就輪替，第 7 章）
access token 走 JWT 讓每個請求的驗證不打 DB（簽章 + 過期檢查就夠）；refresh token 反過來必須存 DB，因為它要支援撤銷、輪替、重用偵測——這些都是「伺服器要記得狀態」的能力。只存雜湊則是防 DB 外洩：撈走整張表也拿不到可用的 token。

5.1 登入流程：三個安全設計

三個設計各自防一種攻擊：

  1. 防 timing attack（①②）：帳號不存在、帳號鎖定時也跑一次 Argon2 dummy 比對。Argon2 故意很慢（十幾毫秒級），不補這一下，攻擊者從回應時間就能判斷「帳號存不存在」。
  2. 防平行暴力猜測：比對密碼之前先用一句原子 SQL「佔用」一次嘗試。就算同時送一萬個請求，也只有前 max-attempts（預設 5）個能真的比對密碼：
  1. 不耗光連線池：login 刻意不包交易。每句 UPDATE 自動 commit，比對密碼（最慢的一步）期間不持有 row lock 也不佔 DB 連線——同一帳號被狂打時，資料庫不會被拖垮。
登入鎖定（以帳號計）和 rate limit（以 IP 計）是互補的：rate limit 擋不了「換 IP 慢慢猜同一個帳號」，登入鎖定擋不了「掃一堆帳號各猜一次」。兩個都要。帳號不存在時不計數（沒有資料列可記），交給 rate limit。

6每個請求的驗證與即時失效

JWT 無狀態驗證有個經典難題：token 簽出去 15 分鐘內怎麼撤銷？這個專案的答案是 token_version + PrincipalCache——每個請求除了驗簽章，還會核對一份「幾乎都命中 Redis 快取」的使用者現況。

6.1 驗證鏈

PublicPathIgnoringBearerTokenResolver公開路徑（/login、/refresh…）不解析 Authorization header——帶著過期 token 來登入不該被擋成 401
↓
NimbusJwtDecoder驗 HS256 簽章、exp、issuer
↓
JwtUserPrincipalAuthenticationConverter查 PrincipalCache → 核對 active 與 token_version → 組 AuthUser + authorities
↓
@PreAuthorize("hasAuthority('user:write')")controller 方法級權限檢查

6.2 即時失效的兩個機制

  • token_version：users 表的整數欄位，簽 JWT 時放進 ver claim。要讓某人所有 token 立即失效（/logout-all、停用帳號、改密碼），把 token_version + 1 即可——所有舊 token 的 ver 對不上，下一個請求就被拒。
  • PrincipalCache：使用者 + 角色 + 權限這份資料每個請求都要，查 DB 是 3 句 SQL，所以快取在 Redis（key auth:principal:{user_id}，TTL 5 分鐘）。細節：
    • 快取值帶「全域 gen + 個人 ver」兩個戳記：evict(userId) 把個人 ver INCR（單人失效）、evictAll() 把全域 gen INCR（角色權限改了、影響很多人時一次全失效），不用掃 key。
    • 交易中呼叫 evict 會等 commit 之後才執行（afterCommit）——先清快取再 rollback 的話，別的請求會把舊資料重新灌回快取。
    • Redis 故障直接退回查 DB（timeout 1 秒），驗證結果不受影響，只是慢一點。
    • 上面代碼裡的 reload 分支處理「token 比快取新」：剛 logout-all 完又立刻登入，新 token 的 ver 比快取裡的大，這時略過快取查 DB，不會把剛簽的合法 token 誤判成無效。

6.3 權限從哪裡來（RBAC）

一般使用者的權限 = 自己角色對應的 permission code；擁有 is_admin 角色的人直接拿全部權限外加 ROLE_ADMIN——新權限上線時不用記得補給 admin。業務代碼取當前使用者用 PrincipalUtil.current() / isSelf() / isAdminOrSystem()。

7Refresh 輪替與重用偵測

refresh token 每用一次就換發新的（rotation），舊的標記為 rotated。同一個登入會話的所有 token 用 family_token_id 串成一條鏈。這個結構讓系統能偵測「token 被偷」：

假設攻擊者偷到一份 refresh token。他用了，拿到新 token——但原主人的 App 之後也會拿「同一份舊 token」來換發。此時伺服器看到一個「已輪替過的 token 又被使用」，無法分辨誰是小偷，但可以確定這條鏈外洩了，正確動作是把整個 family 全部撤銷：雙方都被登出，攻擊者手上的新 token 也作廢。這就是 OAuth2 的 refresh token rotation + reuse detection。
  • noRollbackFor = UnauthorizedException：一般交易遇到例外會 rollback，但這裡「撤銷 family」正是在丟 401 之前做的——rollback 掉就白撤銷了。這行註解值一個版本號。
  • FOR UPDATE 行鎖：兩個請求同時拿同一份 token 來換發時，序列化處理——第二個會看到第一個改完的狀態（rotated），正確觸發重用偵測，而不是兩個都成功。
  • 撤銷原因（RevokedReason）記在資料列上：REUSE_DETECTED / USER_INACTIVE / TOKEN_VERSION_CHANGED / LOGOUT，查案時一眼看懂。
  • 重用偵測同時寫一筆 CRITICAL 告警（auth.token_reuse），detail 帶上這次請求和當初簽發的 UA，可比對是否同一裝置。

8業務模組的分層（user）

user 模組是業務模組的樣板：使用者 / 角色 / 權限 / 個人資料四個子領域，每個都採同一套「讀寫分離」分層。

讀和寫的需求天生不對稱。讀取常要 JOIN、分頁、關鍵字搜尋，產物是給前端看的扁平資料——讓 Controller 直接呼叫 QueryMapper 拿 ReadModel，中間塞一層「只是轉手」的 service 沒有價值。寫入則相反：要交易、要行鎖、要稽核、要權限規則，值得完整的 Command → Service → Repo 三層。各層職責：Command 管用例（交易邊界、@ActivityLog、業務規則）；Service 放可共用的領域邏輯（lockExisting、checkUnique）；Repo 包住 mapper 並把 DuplicateKeyException 轉成 ConflictException。

一個寫入用例的完整要素

  • 行鎖先行（②）：先 FOR UPDATE 鎖住再檢查、再改，兩個管理員同時操作同一人時序列化。
  • 停用必須立即生效（⑤）：光改 status 不夠——對方手上的 access token 還有 15 分鐘壽命。呼叫 security 模組的 logoutAll 把 token_version + 1，配合第 6 章的驗證鏈，下一個請求就被拒。模組依賴是單向的：user → security，反過來沒有。
  • 快取失效的範圍對應影響面：改單一使用者 → principalCache.evict(id)；改角色的權限（影響很多人）→ RoleCommandImpl 用 evictAll()。
  • @ActivityLog 掛在 Command 方法上（不是 controller），和 @Transactional 同進退，記「誰、對誰、做了什麼」。

9.1 收集：每 10 秒一批增量

選 StepMeterRegistry 當基底是關鍵決定：它把「算增量」這件麻煩事全包了——每個 step（10 秒）結束時，counter / timer 讀到的就是這 10 秒內的增量，不是累計值。寫進 DB 的每筆 sample 天然就是「這 10 秒發生了多少」，查詢端不用再做差分。
  • 不寫沒意義的資料：counter 增量 0、histogram 的 count 0 這個 step 不寫（沒流量就沒有 row）；gauge 一律寫（0 也有意義，例如連線池 pending=0）；NaN / Infinity 跳過。
  • DB 寫失敗不影響告警：兩個去向各自 try/catch——DB 抖一下，告警照常評估，不會「DB 出事時監控剛好失明」。
  • timer / summary 這類 histogram 會拆成三筆 sample：count（筆數）、sum（總耗時）、max（最大值）。
listener 是延遲解析的（第一次 publish 才真的去拿）。因為告警 listener 依賴 AlertRecorder → MyBatis mapper → SqlSessionFactory，而 SqlSessionFactory 又為了 SqlLogInterceptor 需要 MeterRegistry——建構時就解析會形成循環依賴，啟動直接失敗。延遲到背景執行緒第一次 publish（context 已 refresh 完）就沒事。

9.2 儲存模型：三層結構

  • 為什麼拆三層：sample 是海量的（每 10 秒一批），把指標名和 tag JSON 從每筆 sample 裡抽出去，sample 表每列只剩 (series_id, recorded_at, type, value)，又窄又好建索引。
  • JSONB attributes：tag 組合不定形，用 JSONB 存，查詢用 @> 部分比對（attributes @> '{"outcome":"SERVER_ERROR"}' 命中所有 5xx 的 series，不管 uri 是什麼）。
  • 寫入端（DatabaseMetricsStore）把 metric 和 series 的 id 快取在內存，穩定狀態下每 10 秒只有一句批次 INSERT sample。
  • outcome 這個 tag 是 Micrometer 內建的 HTTP 狀態分類：SUCCESS=2xx、CLIENT_ERROR=4xx、SERVER_ERROR=5xx——告警規則比對它就不用列舉每個狀態碼。

MetricsMaintenanceScheduler 每 15 分鐘跑一次，順序是關鍵：先把完整的小時彙總進小時表，再刪原始資料，而且只刪已彙總過的部分——彙總失敗這輪就不刪，資料不會掉。彙總寫法可重複執行（idempotent），多跑一次結果相同，所以多台部署也只是多做工不會算錯。

9.4 內存告警

門檻規則寫在 yml（例如「5 分鐘內 5xx 次數 > 0 就 CRITICAL」），但評估完全不查 DB：ThresholdAlertEvaluator 實作 StepListener，直接訂閱 §9.1 那批增量——跟寫進 metrics_sample 的是同一批資料、同一個切點，告警和 UI 看到的數字不會分家。

舊版是每條規則每 10 秒跑一句 aggregate SQL：規則越多 SQL 越多，告警負載跟規則數綁死。改成內存後：穩定狀態整個管線每 10 秒只剩 1 句 SQL（批次 INSERT sample），規則數量跟 SQL 負載完全解耦，告警 INSERT 只在觸發時發生（事件驅動）。代價是重啟後窗口是空的——前一個 window 期間只會少算、不會誤報，可接受。

9.5 監控 UI

/metrics-ui 是一頁自包含的靜態 HTML（跟本教學同一個哲學：不用 CDN，圖表直接畫 SVG），由 metrics 模組的 Controller 從 classpath 讀出來回傳。頁面本身公開，資料 API（/metrics-ui/api/**）要登入——右上角貼 access token。

查詢端的兩個機制：

  • 來源切換：範圍 ≥ 30 天查小時表，其餘查原始表——跟 §9.3 的保留策略互相咬合（14d 範圍貼著原始資料的刪除邊界，最舊的幾桶可能缺資料）。
  • 分桶：一張圖最多 240 個點，桶寬 = 範圍 ÷ 240（下限 10 秒）。查 90 天不會傳 77 萬個點給瀏覽器，SQL 端就先 GROUP BY 時間桶。

10背景清理與部署

10.1 兩種清理排程的對照

專案裡有兩個「刪過期資料」的排程，刻意用了兩種觸發方式，放在一起看很有教學價值：

clean 模組 RetentionSchedulersecurity 模組 RefreshTokenCleanupScheduler
清什麼activity_logs / alerts 超過保留期（預設 730 天）過期超過 7 天的 refresh token
觸發fixedDelay = 24h（啟動後開始算）cron = "0 0 3 * * *"（UTC 固定凌晨三點）
共同點分批刪、可重複執行、單表失敗不影響其他表、多台部署跑多次也只是多做工

還有一個設計值得注意：RetentionCleaner 是純 Java 類，不是 Spring bean。排程殼（RetentionScheduler）只負責「什麼時候跑」，邏輯全在 cleaner 裡——單元測試 new 一個 cleaner、塞假的 mapper 和固定時間就能測完所有分支，不用起 Spring context。

10.2 Docker 打包與部署

  • pom 先行的 layer cache：依賴下載是最慢的一步，把它跟原始碼分開成兩層——改代碼不改 pom 時，重建直接跳過依賴下載。
  • 非 root 執行：建 spring 系統使用者跑 app；exec java 讓 JVM 成為 PID 1，收得到 docker stop 的 SIGTERM，配合 Spring 的 graceful shutdown。
  • runtime 用 JDK 不用 JRE：大一點，換來容器內能用 jcmd 和 attach API 排查（heap dump、Arthas）。

docker-compose 四個服務用 healthcheck 串依賴：postgres / redis healthy → app 啟動；app 的 healthcheck 用 curl 打 /actuator/health，healthy 之後 nginx 才啟動——冷啟動時不會有流量打到還沒 ready 的 app。./logs 掛載到 /app/logs，所有服務 TZ=UTC。

10.3 已知限制（誠實清單）

  • 只支援單機：series 沒有 instance id，多台部署時 gauge 會混在一起；告警窗口在各台內存裡各算各的。
  • app 無法監控自己的死活：指標和告警都在 app 裡，app 掛了就全停，要靠外部打 /actuator/health。
  • 沒有 p95 / p99：只存 count / sum / max，沒存 histogram bucket。
  • 排程只考慮單機：多台時每台都會跑清理與彙總（可重複執行所以結果正確，只是多做工）。
  • 登入鎖定可被惡意利用：知道帳號名稱的人可以故意輸錯把對方鎖住（接受此代價換暴力破解防護）。
  • 預設管理員密碼所有環境相同，上線後要立刻修改。

把限制寫清楚跟把功能做出來一樣重要——每一條都是「知道，但現階段不值得」的決定，而不是沒想到。
