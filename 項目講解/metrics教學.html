指標管線：從 Micrometer 到 DB

這份教學只講一件事：counter.increment() 之後到 metrics_sample 多一列之間，發生了什麼。難懂的原因是這條路有一半藏在 Micrometer 庫裡——排程執行緒、增量切割、filter 關卡都不在專案代碼中。本文由下往上，把每一層藏起來的東西攤開，對應 metrics 模組的真實代碼。

1Micrometer 是什麼

Micrometer 之於指標，就像 SLF4J 之於 log：一個門面（facade）。業務代碼只對著它的 API 計數，「數字最後去哪」由掛上的 registry 決定——官方有 Prometheus、Datadog 等幾十種 registry，這個專案自己寫了一個把數字送進 PostgreSQL 的。

整個體系只有三個核心概念：

概念是什麼例子
Meter一個量測點。Counter、Timer、Gauge 都是它的子型別「app.sql 這個操作的耗時統計」
Meter.Idmeter 的身分 = 名稱 + tag 組合。tag 不同就是不同的 meterapp.sql{statement=UserMapper.findById} 和 {statement=RoleMapper.list} 是兩個 meter
MeterRegistrymeter 的工廠 + 容器：建立 meter、持有所有 meter本專案的 DatabaseMeterRegistry

2Meter 的種類

不同的量測需求用不同型別，差異在「存了什麼、怎麼結算」：

型別語義例子內部存什麼
Counter只增不減的計數auth.login.failure、app.sql.slow一個累加的 double
Gauge「當下值」，可升可降；不是你去 set，而是它去讀——註冊時給一個函式，取值時才呼叫jvm.memory.used、hikaricp.connections.active一個函式參考
Timer耗時分佈：每 record 一次，同時累積次數、總時間、最大值http.server.requests、app.sqlcount + sum + max
DistributionSummary跟 Timer 一樣，但量的不是時間（例如 payload bytes）—count + sum + max

這張表直接決定了資料庫裡的兩個 type 欄位（第一份教學 §9.2 的那張圖）：

Meter 型別metrics.type每個 step 產生的 metrics_sample.type
Gaugegaugevalue ×1（當下值）
Countersumvalue ×1（這 10 秒的增量）
Timer / Summaryhistogramcount + sum + max ×3（這 10 秒的）
Timer 為什麼拆三筆？因為「平均耗時」不能直接存——不同時間桶的平均數無法再平均。存 count 和 sum，查詢端隨時能算任何範圍的平均（Σsum ÷ Σcount），max 則回答「最糟的那次多慢」。這也是為什麼沒有 p95：percentile 需要存整個分佈（bucket），這裡刻意不存（已知限制）。

3誰在量測：meter 哪來的

metrics UI 上有 69 個指標，但專案裡搜 Counter.builder 只找得到幾個——大多數 meter 是 Spring Boot 自動綁上來的。機制：Spring Boot 的 metrics autoconfiguration 會找出 context 裡所有 MeterRegistry bean，把一批「binder」接上去。本專案的 registry bean 就是 DatabaseMeterRegistry（MetricsStoreConfig 裡 @Bean），所以這些自動量測全部流進它：

指標誰在量怎麼量
http.server.requestsSpring Boot 的 WebMVC 量測 filter每個請求結束時 timer.record(耗時)，tag 帶 uri（路由樣板）、method、status、outcome、exception
jvm.*、process.*、system.*JvmMemoryMetrics 等 binder註冊一堆 Gauge，函式直接讀 MXBean
hikaricp.connections.*HikariCP 自帶的 Micrometer 整合Gauge 讀連線池狀態
app.request.slow專案：RequestLogFilter超過門檻的請求 counter +1
app.sql / app.sql.slow專案：SqlLogInterceptor第 1 章那段代碼
auth.login.failure / auth.refresh.failure專案：AuthServiceImpl每種失敗原因（reason tag）counter +1
app.rate_limit.rejected專案：RateLimitInterceptor被擋的請求 counter +1，tag 是規則名
所以「指標在哪裡量」這個問題的答案很分散——這是設計使然：量測代碼就住在它量的東西旁邊（SQL 計時在 SQL 攔截器裡、登入失敗在登入代碼裡），registry 是它們唯一的交會點。而 outcome=SERVER_ERROR 這類 tag 是 Spring Boot 的量測 filter 自己加的（HTTP 狀態分類：2xx=SUCCESS、4xx=CLIENT_ERROR、5xx=SERVER_ERROR），不是專案代碼。

4MeterFilter：誕生時的關卡

自動量測有個危險：你控制不了它產生多少 meter。每個 uri × method × status 組合都是一個新 meter（新 series），遇到被亂掃的 404 路徑或帶 id 的 uri，meter 數會失控。Micrometer 的解法是 MeterFilter：每個「新」meter 進 registry 前（第 1 章 register 的第二步）要過關：

map(id)可以改寫 Meter.Id：這裡用來「拿掉不要的 tag」（ignore-tags）
↓ 改寫後的 id 再進入
accept(id)回 DENY / NEUTRAL / ACCEPT。DENY 的 meter 會變成 no-op：業務代碼照常 increment，但數字直接丟掉
  • ③ 是防爆炸的最後防線：某個 tag（例如 uri）的不同值超過上限後，帶新值的 meter 不再建立（已存在的照常計數），並 WARN 一次。被掃描器亂打一萬個路徑，最多也只產生上限個 series。
  • 這個 filter 怎麼掛上 registry 的？又是隱藏機制：MetricsFilterConfig 只是把它宣告成 @Bean，Spring Boot 自動把所有 MeterFilter bean 套用到所有 registry——專案裡找不到 registry.config().meterFilter(...) 這行，是 Boot 代勞的。
  • 設定來源是 application.yml 的 app.metrics 段：deny 前綴清單 + 每個指標的 rules（deny / ignore-tags / max-tag-values）。

5Step 機制：增量怎麼切

這是整條管線最「看不見」的一層，也是選 StepMeterRegistry 當基底的原因。先理解問題：

Counter 天生是累計值：開機到現在共 12,345 次。但圖表和告警要的是增量：「這 10 秒發生了幾次」。如果存累計值，查詢端得自己對相鄰兩點做差分，還要處理重啟歸零（數字突然掉回 0 會算出負增量）。Prometheus 走的是「存累計、查詢時差分」路線（rate() 函式）；Step 體系走反路線：在源頭就把時間切成固定的格子（step），每格結束時結算這一格的增量。存進 DB 的每筆就是乾淨的增量，查詢端零負擔。

實現手法是雙槽輪替（rollover）。每個 step 型 meter 內部有兩個槽：

  • 所以 DatabaseMeterRegistry.publish() 裡的 counter.count()、timer.count() 讀到的不是累計值，是上一個 step 的增量——這是最容易誤解的一點，代碼表面看不出來，語義由父類決定。
  • rollover 是惰性的：取值時發現「現在已經跨到新的 step 了」才搬槽，不需要額外的執行緒盯著。
  • Gauge 不參與這套機制——它沒有累積可言，取值就是當場呼叫那個函式讀當下值。
  • step 的長度就是先前追過的那條設定鏈：app.metrics.store.step: 10s → MetricsStoreProperties → 建構子 → StepRegistryConfig.step()。

6執行緒與生命週期

「每 10 秒」到底是誰在跑？專案裡沒有任何 @Scheduled 或 Timer 對著 publish——答案在 bean 定義的最後一行：

registry.start(...) 是 StepMeterRegistry（父類）的方法：起一個單執行緒排程器，每 step() 間隔呼叫一次子類的 publish()。執行緒名叫 metrics-store——thread dump 或 log 裡看到這個名字，就是它。整條管線跑在哪些執行緒上，值得一張總表：

執行緒做什麼多常
HTTP worker（Tomcat）increment() / record()：改內存數字每個請求，奈秒級
metrics-storepublish()：掃 meter → 寫 DB → 通知告警 listener（RuleWindow 只在這條執行緒上被碰，所以不用鎖）每 10 秒
Spring schedulingStoreStalledChecker（看門狗——metrics-store 執行緒死了只有別條執行緒能發現）；MetricsMaintenance（彙總 + 清理）10 秒 / 15 分鐘

生命週期的另一端是 destroyMethod = "close"：Spring 關 context 時呼叫 registry 的 close()（也是父類的，專案沒覆寫）——停掉排程執行緒、把「最後一個不滿 10 秒的 step」強制結算再 publish 一次。配上 Dockerfile 的 exec java（JVM 是 PID 1，收得到 SIGTERM）和 graceful shutdown，停機前最後幾秒的請求數不會蒸發。

這個 bean 還埋著本專案踩過最深的坑：循環依賴。registry 建構時如果立刻解析 listener，鏈路是 ThresholdAlertEvaluator → AlertRecorder → MyBatis mapper → SqlSessionFactory，而 SqlSessionFactory 又為了 SqlLogInterceptor（它要記 app.sql 指標）需要 MeterRegistry——回到正在建的這個 registry，啟動爆炸。解法是兩處都「延遲解析」：store 的 mapper 用 Supplier（上面 mapper::getObject），listener 清單也用 Supplier，都拖到第一次 publish（metrics-store 執行緒上，context 早已組裝完）才真的去拿。ObjectProvider 就是 Spring 給「先拿著、要用再查」設計的工具。

7publish()：meter 變成 sample

每 10 秒，metrics-store 執行緒呼叫一次這個方法。它是整條管線「從 Micrometer 世界跨進專案世界」的翻譯層：把活的 meter 物件翻成不可變的 MetricSample record，然後送往兩個去向。

meter.use(...) 是 Micrometer 的型別分發（八個 lambda 對應八種 meter 型別，比 instanceof 鏈乾淨）。各型別的轉換規則：

型別轉成不寫的情況（省掉無意義的 row）
Gauge / TimeGaugevalue ×1：當下值NaN / Infinity（gauge 的函式可能讀到無效狀態）；0 照寫——「連線池 pending=0」是有意義的資訊
Counter / FunctionCountervalue ×1：這 step 的增量（第 5 章）增量 0：這 10 秒沒發生就沒有 row
Timer / Summary / LongTaskTimercount + sum + max ×3count 0：沒流量的操作不佔三列
  • 兩個去向各自 try/catch：DB 壞掉不影響告警評估（告警反而更該活著）、某個 listener 丟例外不影響 DB 寫入和其他 listener。
  • recordedAt 取自 registry 的 Clock——跟 step 切割用同一個時間來源，整批 samples 共用同一個時間戳：這就是「告警和 UI 看同一個切點」的保證。
  • 時間單位：getBaseTimeUnit() 回 MILLISECONDS，所以 timer 的 sum/max 存進 DB 的單位是毫秒（metrics.unit = milliseconds）。

8寫入 DB 的那一句 SQL

去向①的終點是 DatabaseMetricsStore。它要解決的問題：sample 帶的是「名稱 + tag map」，但 DB 要的是 series_id（三層模型）。每批幾百筆 sample，不能每筆都去查 id——所以 id 查一次就快取在內存：

  • 穩定狀態 = 每 10 秒 1 句 SQL。所有 metric / series 的 id 都已在快取裡，剩下的只有那句批次 insertSamples。只有「第一次出現的 meter」才會多兩句 INSERT + SELECT 登記。
  • 登記用 INSERT ... ON CONFLICT DO NOTHING 再 SELECT——多台 instance（或重啟後快取清空）同時登記同一個 series 也不會撞唯一鍵。
  • normalize 的 TreeMap 排序是容易忽略的關鍵：tag map 的序列化順序若不固定，同一組 tag 會被登記成多條 series，圖上同一條線裂成好幾條。
  • 寫完順手更新 MetricsWriteState.saved(recordedAt)（第 6 章 bean 定義裡那個 lambda 包裝）——這個 volatile 時間戳就是 store-stalled 看門狗盯的對象。
