整理自 Robert Heaton 的〈Systems design for advanced beginners〉（2020）。原文用一個虛構的二手交易平台「Steveslist」當例子，把一家網路公司五年後會有的系統走過一遍。這篇是我消化後重寫的版本：結構重排過，補了原文沒講的背景與常見的坑，原文說錯或過時的地方另外標出來。

先講重點

一個「會寫小網站」的人和「看得懂大型平台」的人，差別不在某個高深技術，而在知道有哪些零件、每個零件解決什麼問題、代價是什麼。這篇要記住的只有幾件事：

  1. 對外只有三種入口：瀏覽器、手機 App、API。三者本質上都是「送 HTTP 請求給伺服器、拿回資料」。
  2. 主資料庫是唯一的真相來源（source of truth）。搜尋引擎、資料倉儲裡的資料都是從它複製出去的副本，掉了可以重建。
  3. 沒有最好的資料庫，只有適合某種查詢的資料庫。精確查詢用關聯式資料庫，模糊搜尋用搜尋引擎，全公司的大統計用資料倉儲。
  4. 資料量大了就分片（sharding），怕機器掛就複寫（replication），怕全毀就備份（backup）。三件事解決的是三個不同的問題，不能互相取代。
  5. 不需要使用者等的事就丟到背景做（pub/sub、排程工作）。代價是你得處理「重複執行」和「晚一點才一致」。
  6. 幾乎每個選擇都是速度、正確性、複雜度三者的取捨。原文作者自己也說：現實中很多技術選型的真正理由是「某人剛好很熟這個」和「當時隨手選的，後來沒空重新評估」。

什麼是伺服器

伺服器（server）就是一台掛在網路上、等別的電腦來找它的電腦（更精確地說，是上面跑的那支程式）。收到資料後做點事，通常再回傳一些資料。

  • 網頁伺服器：等 HTTP 請求，回傳網頁或資料。
  • 資料庫伺服器：等查詢語句，讀寫它管理的資料。

補充兩個常被混用的詞：

  • 應用伺服器（application server）：跑你自己寫的商業邏輯的那些機器。
  • 「伺服器」有時指實體機器、有時指虛擬機、有時指一支行程。現在一台實體機上常跑很多個容器，所以談架構時講的通常是「角色」而不是「幾台機器」。

對外的三個入口

網頁：單頁應用（SPA）

單頁應用（Single-Page Application）的「單頁」是指：使用者在站內點來點去時，瀏覽器幾乎不用整頁重新載入。

流程是：

  1. 瀏覽器第一次請求，伺服器回一份幾乎空的 HTML 骨架。
  2. 骨架叫瀏覽器再去抓一大包 JavaScript。
  3. JavaScript 在瀏覽器裡執行，負責畫出畫面。
  4. 之後需要資料時，JavaScript 在背景向伺服器的 API 發請求，拿到資料後只更新畫面的一小塊。

相對的是傳統的多頁網站：每點一個連結，伺服器就產生一整頁新的 HTML。原文舉的例子是作者自己的部落格（多頁）對比 Twitter（單頁）。

和原文不同：原文說背景請求叫「Asynchronous JavaScript XML Request」。AJAX 的正確全名是 Asynchronous JavaScript and XML。而且這個名字現在只剩歷史意義：實際傳的幾乎都是 JSON 而不是 XML，寫法上也多半用瀏覽器內建的 fetch，而不是早期的 XMLHttpRequest。

原文只說 SPA「做起來很費工但很好看」，這太簡略了。實際要考慮的是：

單頁應用 伺服器產生頁面
站內切換 快，像 App 每次整頁重載
第一次開啟 慢，要先下載並執行大量 JavaScript 快，HTML 來了就能看
搜尋引擎收錄 較麻煩，內容是 JavaScript 畫出來的 天生沒問題
開發複雜度 高，前端要管理狀態、路由 低
適合 互動密集的工具（信箱、後台、編輯器） 內容為主的網站（部落格、文件、商品頁）

現在常見的折衷是伺服器端渲染（SSR）：第一頁由伺服器產生完整 HTML，載入後再由 JavaScript 接手變成單頁應用，Next.js、Nuxt 這類框架就是做這件事。所以「要不要做 SPA」不是二選一。

手機 App

App 和網頁前端做的是同一件事：發 HTTP 請求給伺服器、拿回資料、更新畫面。所以後端可以共用同一套 API，額外的工作只有 App 本身的介面。

也可以用跨平台框架一份程式碼出 iOS 和 Android，例如 React Native（寫 JavaScript）或 Flutter（寫 Dart）。

原文沒提、但實務上很重要的一點：App 一旦發出去就收不回來。網頁改版後所有人下次開就是新版，但使用者手機裡的舊版 App 可能會存在好幾年，而且繼續呼叫你的 API。所以給 App 用的 API 必須向下相容，改動要用版本號區隔（這也是下面網址裡有 /v1/ 的原因）。

API

API 讓別人寫程式來操作你的平台，例如一次上架幾百件商品。做法是對你公開的**端點（endpoint）**發 HTTP 請求，例如 GET api.steveslist.com/v1/listings 取得自己的所有商品。回應用 JSON 格式：

json{
  "listings": [
    {
      "id": 2178123867,
      "name": "TV",
      "city": "San Francisco",
      "price_amount": 1000,
      "price_currency": "usd"
    }
  ]
}

JSON 是純文字的結構化格式，任何語言都能輕易解析，和 JavaScript 已經沒有綁定關係。

和原文不同：原文的 JSON 範例裡用 # 寫註解。JSON 標準不允許任何註解，真的這樣回傳，對方的解析器會直接報錯。

身分驗證：使用者在設定頁拿到一組 API 金鑰（API key），一串很長的隨機字串，等於程式用的密碼。每個請求都把它放在 HTTP 標頭（header）裡，伺服器查這把金鑰屬於誰，就以那個人的身分執行。

直接用 HTTP 函式庫呼叫 API 長這樣：

pythonimport requests

response = requests.post(
    "https://api.steveslist.com/v1/listings/",
    data={"name": "TV", "city": "San Francisco", "price_amount": 1000, "price_currency": "usd"},
    headers={"X-Steveslist-API-Key": "YOUR_API_KEY"},
)

原文對 API 只講到這裡。真的要對外開放 API，還得處理這些：

  • 一定要走 HTTPS。金鑰放在標頭裡，沒加密就等於明文廣播密碼。
  • 金鑰要能撤銷與輪替，最好能限制權限範圍（例如唯讀）。伺服器端存金鑰時也應該只存雜湊值，道理和密碼一樣。
  • 限流（rate limiting）：限制每把金鑰每分鐘能打幾次，否則一支寫壞的迴圈就能拖垮你。
  • 分頁（pagination）：「取得所有商品」不能真的一次回傳全部。
  • 冪等（idempotency）：對方網路逾時後重送「建立訂單」，不能建出兩筆。常見做法是請求帶一個唯一的 idempotency key，伺服器看到重複的 key 就回傳上次的結果。這個觀念在後面的 webhook 和 pub/sub 會一再出現。
  • 版本管理：/v1/ 讓你之後能推出不相容的 /v2/ 而不弄壞既有使用者。

Client library

要每個開發者自己組 HTTP 請求太麻煩，所以平台通常會提供各語言的 client library（常被稱為 SDK），把 API 包成一般的函式呼叫：

pythonimport steveslist

listing = steveslist.Listing.create(
    name="TV", city="San Francisco",
    price_amount=1000, price_currency="usd",
    api_key="YOUR_API_KEY",
)

函式庫內部還是在發一樣的 HTTP 請求。它的價值在於把重試、錯誤處理、分頁、簽章驗證這些容易寫錯的事一次做對。代價是平台方得同時維護很多語言的版本，所以現在多半是先寫一份 API 規格（例如 OpenAPI），再用工具自動產生各語言的函式庫。

Webhook：平台主動通知你

API 是「你問平台」。但很多時候使用者要的是「有事發生時平台告訴我」，例如商品賣出時自動寄感謝信並通知倉庫出貨。

笨方法是輪詢（polling）：每隔幾秒問一次「有新訂單嗎？」。絕大多數的回答都是「沒有」，白白浪費雙方資源，而且有延遲。

Webhook 就是反過來的 API：使用者先告訴平台一個網址，事件發生時平台對這個網址發一個 HTTP 請求，內容是事件的細節（商品編號、價格、買家地址…）。使用者在那個網址架一台伺服器，收到後執行自己的邏輯。

買家付款 ──> 平台伺服器 ──(HTTP POST 事件內容)──> 賣家的 webhook 伺服器 ──> 寄信、出貨

Webhook 有兩個麻煩：安全和可靠。

安全：怎麼知道這個請求真的是平台發的

賣家的 webhook 網址是公開在網路上的，任何人知道網址就能送假的「已付款」通知來騙貨。網址不公開不算防護，「藏起來」不等於「安全」。

解法是簽章：

  1. 賣家啟用 webhook 時，平台產生一把隨機的共享密鑰，只有平台和賣家知道。
  2. 平台每次發 webhook，用密鑰和請求內容算出一個簽章，隨請求一起送出。
  3. 賣家的伺服器用同一把密鑰、同樣的算法自己算一次，和收到的簽章比對。一致才處理，不一致就丟掉。

沒有密鑰的人算不出正確的簽章，所以偽造不了。

和原文不同：

  • 原文說 HMAC 是「一種密碼學雜湊函式」。不精確。HMAC 是一種用雜湊函式搭建出來的訊息驗證碼（MAC）構造，實際使用時會講明底層的雜湊，例如 HMAC-SHA256。差別在於：單純的雜湊誰都能算，HMAC 要有密鑰才能算。
  • 原文把簽章放在請求的 JSON 內容裡。實務上簽章都放在 HTTP 標頭，因為簽的對象就是整個請求內容，放在內容裡會變成「簽章要簽到自己」。Stripe 用 Stripe-Signature 標頭，GitHub 用 X-Hub-Signature-256。
  • 嚴格說這是「訊息驗證碼」而不是「數位簽章」。雙方持有同一把密鑰，所以只能證明「是知道密鑰的人發的」，不能向第三方證明是誰發的。業界習慣上還是叫它 webhook 簽章。

原文漏掉的三個實作細節，每一個漏了都會出事：

  • 防重放（replay）：攻擊者就算偽造不了，也可以攔下一個真的請求之後原封不動再送一次。所以簽章要連同時間戳一起簽，接收方拒絕太舊的請求。Stripe 的做法是標頭裡帶 t=時間戳,v1=簽章，官方函式庫預設只接受 5 分鐘內的請求。
  • 用原始的請求內容驗證：必須拿收到的原始位元組去算。如果先把 JSON 解析成物件再轉回字串，欄位順序或空白可能改變，簽章就永遠對不上。這是最常見的踩坑。
  • 用固定時間的比較函式：比對簽章時不要用一般的字串相等，要用語言提供的 constant-time 比較（例如 Python 的 hmac.compare_digest），避免從回應時間的細微差異被猜出簽章。

還有一點原文說得很對：驗證程式是賣家自己寫的，平台只能提供範例和函式庫，沒辦法強迫對方驗證。

可靠：送失敗了怎麼辦

連不上對方伺服器怎麼辦？連上了但對方回錯誤？送出去後對方卡了二十秒然後斷線，到底有沒有收到？

平台必須選一種保證。常見的是至少一次（at-least-once）：只要不確定成功，就一直重試（次數有上限）。副作用是同一個 webhook 可能送到兩次，所以接收方必須自己處理重複。

補充三種傳遞保證，後面 pub/sub 也是同一套觀念：

保證 意思 代價
至多一次（at-most-once） 送一次就不管了 可能掉訊息
至少一次（at-least-once） 不確定就重送 可能重複
剛好一次（exactly-once） 不掉也不重複 在不可靠的網路上無法單靠傳送端做到

實務上的答案幾乎都是「至少一次 + 接收方做成冪等」。接收方的標準做法：

  • 每個事件帶唯一的 event ID，處理前先查「這個 ID 處理過了嗎」，處理過就直接回成功。
  • 先快速回 200，再處理。收到後把事件丟進自己的佇列就回應，耗時的工作在背景做。否則處理太久會被平台當成逾時而重送。
  • 不要假設事件會按順序到達。
  • 平台端重試時通常採用指數退避（間隔越拉越長），連續失敗太久就停用這個網址並通知使用者。

用密碼登入

原文只談密碼登入，其他方式（如 OAuth）略過。

鐵則：任何地方都不能存明文密碼。資料庫不行、日誌檔不行、任何中間系統都不行。密碼外洩的傷害不只是你這個站：很多人在各個網站用同一組密碼，你被偷等於他們在別處的帳號也被偷。

做法是存雜湊值。雜湊函式是單向的：從輸入算出雜湊很容易，從雜湊反推輸入實際上做不到。登入時把使用者輸入的密碼再算一次雜湊，和資料庫裡存的比對。資料庫被偷，攻擊者拿到的也只是雜湊值。

原文過度簡化的地方：原文說「用 bcrypt 這類雜湊函式」就帶過了，沒講為什麼是 bcrypt，也完全沒提「鹽」。這兩點正是密碼儲存的核心。

為什麼不能用一般的雜湊（如 SHA-256）：一般雜湊的設計目標是「快」，一張顯示卡每秒能算幾十億次。攻擊者拿到雜湊後不需要「反推」，只要把常見密碼一個個算過去比對就好，快的雜湊等於幫攻擊者加速。密碼要用故意設計得很慢、而且慢的程度可調的專用演算法，讓每猜一次都要付出可觀的成本。

鹽（salt）：替每個使用者產生一段隨機值，和密碼一起雜湊，鹽本身明文存在旁邊。作用有兩個：

  • 相同的密碼會得到不同的雜湊，攻擊者看不出誰和誰用同一組密碼。
  • 攻擊者不能用事先算好的對照表（彩虹表），也不能算一次就同時比對所有人，必須對每個人分別重算。

bcrypt、Argon2 這類演算法會自動產生鹽，並把鹽和參數編在輸出的字串裡，所以不要自己實作，用語言生態裡成熟的函式庫，呼叫它的 hash 和 verify 就好。

現在該選哪個（依 OWASP 的密碼儲存建議）：

演算法 定位
Argon2id 新系統的首選。除了耗時間還耗記憶體，更能抵抗用顯示卡或專用硬體的大量猜測
scrypt Argon2id 不可用時的替代
bcrypt 舊系統常見，仍可接受。注意它只處理密碼的前 72 個位元組
PBKDF2 需要符合 FIPS 規範時使用

具體參數（記憶體大小、迭代次數）會隨硬體進步而調高，要用時去看 OWASP 當下的建議，不要抄舊文章上的數字。

別把密碼寫進日誌。這是最容易犯的錯：為了除錯把每個請求的所有參數都記下來，登入請求裡的密碼就跟著進了日誌。原文舉 Facebook 當例子，這件事是真的：2019 年 3 月資安記者 Brian Krebs 揭露、Facebook 隨後承認，有數億個帳號的密碼以明文留在內部日誌裡，部分可追溯到 2012 年，上萬名員工有權限搜尋到。Facebook 的密碼資料庫本身有正確地雜湊加鹽，出事的是日誌。所以防護要做在日誌層：對 password、token、authorization 這類欄位一律遮蔽。

原文沒提、但登入系統一定要有的：

  • 登入失敗的限流與鎖定，擋住線上暴力猜測。
  • 多因素驗證（MFA）。
  • 註冊與改密碼時比對已外洩的密碼清單，拒絕 12345 這種密碼。
  • 演算法參數調高後，在使用者下次成功登入時順手用新參數重算雜湊。

主資料庫怎麼長大

主資料庫是關聯式資料庫（原文用 MySQL）。資料庫不是魔法，它是跑在電腦上的程式，資料多了硬碟會滿、查詢會慢。

一開始最簡單的做法是換一台更大的機器，這叫垂直擴充（scale up）。它的好處是完全不用改程式，所以該用就用。但單機有上限，而且越頂級的機器越貴。超過之後只能把資料分散到多台機器，叫水平擴充（scale out）。

先釐清三個容易搞混的概念：

解決的問題 做法
分片 sharding 資料太多、寫入太多，一台裝不下 把資料切開，每台放不同的一部分
複寫 replication 機器會壞；讀取量太大 把同一份資料即時複製到多台
備份 backup 整個毀掉、或資料被改壞 定期把資料另存到別處

大型系統三個都會用：資料先分片，每個分片再各自複寫成好幾份，再加上定期備份。

分片

把資料切成一塊一塊（shard），每塊放在不同的機器上，全部機器合稱一個叢集（cluster）。

用什麼切（分片鍵，shard key）取決於你的查詢方式。原文的例子是按使用者切：同一個使用者的個人資料、商品、訊息都在同一台機器上，這樣「查某個使用者的東西」只需要問一台。不屬於任何使用者的資料（例如「今日特賣」）可以用別的鍵切，量小的話乾脆不切。

誰知道資料在哪台：需要一層路由。

做法 優點 缺點
應用伺服器自己帶著分片對照表 少一次轉送，比較快 對照表一改，所有應用伺服器都要同步更新
中央路由器，所有查詢先送給它 對照表只需改一個地方 多一次轉送；路由器本身不能掛

怎麼決定誰去哪個分片，原文只舉了「奇數 ID 去一號、偶數去二號」和「特定大戶獨佔一個分片」。整理成三種策略會更清楚：

策略 做法 優點 缺點
範圍 ID 1 到 10000 在一號，10001 到 20000 在二號 簡單；範圍查詢方便 容易不均，新資料全擠在最後一個分片
雜湊 對 ID 做雜湊再取餘數 分布均勻 範圍查詢要問所有分片；增加分片時麻煩（見下）
對照表 另外存一張「誰在哪個分片」的表 最有彈性，可以把大戶單獨搬走 多一次查表；對照表本身要高可用

原文說的「絕大多數隨機分配，但某個大戶獨佔一個分片」，就是雜湊加上對照表的例外。

原文沒講的坑：用取餘數分片，增加機器時幾乎所有資料都要搬家。從 2 台變 3 台，ID % 2 和 ID % 3 的結果大多不同。常見的解法是一致性雜湊（consistent hashing），或是先切成很多個「邏輯分片」（例如 1024 個）再把邏輯分片對應到實體機器，加機器時只搬動一部分邏輯分片。

分片的真正代價（原文完全沒提，但這才是不該輕易分片的原因）：

  • 跨分片的查詢很痛。「列出全站最新的 20 件商品」得問每一個分片再合併。
  • 跨分片的 JOIN 和交易基本上沒了。A 使用者付錢給 B 使用者，兩人在不同分片，就不再是一個單純的資料庫交易。
  • 分片鍵選錯很難改，等於整個資料庫重新搬一次。
  • 維運複雜度大增：改表結構、備份、監控都要乘上分片數。

所以實務上的順序通常是：加索引和改寫慢查詢 → 加快取 → 換更大的機器 → 加唯讀副本分擔讀取 → 把不相關的資料表拆到不同的資料庫 → 最後才分片。很多產品一輩子都走不到最後一步。

線上搬資料的步驟（分片滿了要拆、或要換資料庫時通用）：

  1. 雙寫：新資料同時寫到舊的和新的，讀取仍然只讀舊的。
  2. 回填：把既有的舊資料複製到新的那邊，雙寫持續進行。
  3. 驗證：確認兩邊資料一致。可以比對快照，也可以讓每次讀取同時讀兩邊、不一致就告警。
  4. 切換讀取到新的那邊，雙寫繼續，萬一出事還能切回去。
  5. 穩定後停止雙寫，刪掉舊的。

這個「雙寫 → 回填 → 驗證 → 切換 → 清理」的模式值得記起來，幾乎所有不停機的資料遷移都是這個套路。

有些資料庫內建自動分片，不必自己做路由，例如 MySQL 上的 Vitess、PostgreSQL 的 Citus，以及原生就是分散式的 CockroachDB、MongoDB、Cassandra。

複寫

把同一份資料幾乎即時地複製到多台機器。好處有兩個：

  • 容錯：一台掛了，其他副本馬上頂上，使用者可能完全沒感覺。
  • 分擔讀取：讀取請求可以分散到各個副本。

原文沒說清楚的地方：複寫只能擴充讀取能力。每一筆寫入還是要寫到每一個副本，所以加再多副本，寫入能力也不會增加。寫入撐不住時靠的是分片。

原文用了一個很好的比喻，值得留著：想像一間銀行的客服中心，每個客服都是一台資料庫，客戶打電話來轉帳或查餘額，客服之間靠互相打電話同步帳本。資料庫叢集遇到的問題和這間客服中心一模一樣：

  • 兩個客戶同時打給兩個客服，要改同一筆資料，聽誰的？
  • 所以規定只有一位「組長」能受理轉帳，其他人只能回答查詢。那組長剛收到一筆轉帳、還沒告訴別人就昏倒了呢？
  • 某個客服恍神了幾秒，漏聽了組長的幾次更新呢？
  • 如果我們根本無法確定哪個客服還醒著呢？

這些問題對應到實際的架構選擇：

架構 做法 特性
單一主節點（leader-follower） 只有主節點接受寫入，其他副本只能讀 最常見也最單純，不會有寫入衝突；主節點掛了要選新的
多主節點（multi-leader） 多台都能寫 適合跨地區部署；必須處理寫入衝突
無主節點（leaderless） 任何節點都能寫，靠多數決判定 Cassandra、DynamoDB 這類；可用性高，一致性較弱

同步還是非同步是最大的決定。先講這兩個詞本身，它們在系統設計裡到處出現，意思始終一樣：

  • 同步：發起的人等事情做完才繼續。像是去郵局寄信，然後坐在郵局等到對方簽收才回家。
  • 非同步：發起的人不等，交代完就去做別的事。真實的郵局就是非同步的，頂多事後通知你「已簽收」。

套用到複寫：

同步複寫 非同步複寫
做法 主節點等所有副本都寫完，才回覆「寫入成功」 主節點自己寫完就回覆成功，複製在背景進行
速度 慢 快
掉資料的風險 回覆成功就一定都寫進去了 主節點回覆成功後、複製完成前掛掉，這筆資料就消失了，而客戶端以為寫成功了
副本故障時 任何一台副本慢或掛，寫入就卡住 不受影響

原文過度簡化的地方：原文把同步複寫描述成「比較慢但比較安全」。但「等所有副本」有個嚴重的代價：只要有一台副本故障，整個系統就不能寫入，可用性反而變差。所以實務上幾乎沒有人用純粹的全同步，而是用半同步（semi-synchronous）：只要有至少一台副本確認收到就回覆成功，其餘的繼續非同步。這樣保證資料至少存在兩台機器上，又不會被最慢的那台拖累。

原文沒提到、但一用唯讀副本就會遇到的問題：複寫延遲（replication lag）。非同步複寫下，副本的資料會比主節點晚一點點。使用者剛改完暱稱，下一個請求剛好被分到還沒同步的副本，就會看到舊的暱稱，以為沒改成功。常見的處理是「自己剛寫過的資料，短時間內從主節點讀」。

選哪種取決於這筆資料錯了有多嚴重：按讚數慢幾秒或差一兩個沒關係，帳戶餘額就不行。

最後一個坑：主節點掛掉後，如果兩台副本都以為自己是新的主節點，就會各自接受寫入，資料從此分岔，這叫腦裂（split brain）。要正確地「選出唯一的主節點」得靠共識演算法（Raft、Paxos），這也是原文比喻裡「無法確定誰還醒著」那個問題的正式解法。想深入的話，Martin Kleppmann 的《Designing Data-Intensive Applications》第 5 章是這個主題最好的教材。

備份

備份是定期把整個資料庫複製一份，存到遠離正式環境的地方，是最後一道防線。

為什麼有了複寫還要備份：原文的說法是「複寫防單機故障，備份防機房全毀」。這是對的，但還有一個更常見、原文沒明講的理由：複寫會忠實地複製你的錯誤。工程師不小心執行了沒加條件的 DELETE、程式有 bug 把資料寫壞、被勒索軟體加密，這些變更會在幾毫秒內同步到每一個副本。這種時候只有備份救得了你。

用原文的銀行比喻：複寫是接電話時同時抄在好幾本帳本上，怕弄丟其中一本；備份是每天把帳本影印一份鎖進保險櫃。

從備份還原是慢的，使用者一定會感覺到：系統在還原完成前可能整個停擺。

原文過度簡化的地方：原文說還原後「會失去最後一次備份之後的所有更新」。只有每日完整備份時確實如此，但現在的標準做法是完整備份加上持續保存資料庫的變更日誌（MySQL 的 binlog、PostgreSQL 的 WAL），這樣可以還原到任意一個時間點（point-in-time recovery），損失可以縮到幾秒到幾分鐘。雲端的託管資料庫大多內建這個功能。

談備份時會用到兩個指標：

  • RPO（Recovery Point Objective）：最多能接受掉多久的資料。決定備份的頻率。
  • RTO（Recovery Time Objective）：最多能接受停機多久。決定還原流程要多快。

以及三條實務守則：

  • 沒演練過還原的備份不算備份。定期真的拿備份還原一次，很多團隊是出事當天才發現備份檔是壞的。
  • 備份要放在不同的地方：不同機房、不同雲端帳號。和正式資料放在一起的備份會一起毀掉、一起被刪。
  • 備份裡有完整的使用者資料，要加密，存取權限要比正式環境更嚴。

其他的資料系統

全文搜尋

關聯式資料庫擅長精確的查詢：某個使用者最近 90 天的商品、某個編號的商品、舊金山每天新增幾件電子產品。這些查詢的條件都是等於、大於這種明確的比較。

sqlSELECT * FROM items
WHERE user_id = 145122 AND created > NOW() - INTERVAL 90 DAY;

但使用者在搜尋框打「二手電視」時，要的是另一種東西。用 SQL 的 LIKE '%二手電視%' 來做會有三個問題：

  • 只比對得到完全相同的字串。「電視 二手」「2手電視」「二手電是」（打錯字）全都找不到。
  • 沒有相關性排序。使用者要的不是「最新的在前」，而是「最符合的在前」，這是個模糊的概念。
  • 慢。開頭是 % 的 LIKE 用不到一般的索引，只能把整張表每一列掃過一遍。（這點原文沒講，但這才是資料一多就撐不住的主因。）

所以需要專門的搜尋引擎，原文舉的是 Elasticsearch。原文說「不用管它怎麼運作」，但知道核心原理其實不難，而且很有幫助：

  • 倒排索引（inverted index）：一般索引是「這篇文件裡有哪些詞」，倒排索引是反過來記「這個詞出現在哪些文件」。查詢時直接查詞，不用掃全部文件。和書本最後面的索引是同一個道理。
  • 分析（analysis）：建索引前先把文字切成詞，轉小寫、把 running 和 runs 還原成 run、去掉沒意義的字。查詢字串也做同樣的處理，所以大小寫和詞形變化不影響結果。
  • 相關性評分：預設用 BM25 演算法，大意是「查詢的詞在這篇文件裡出現得越多、在所有文件裡越罕見，分數越高」。
  • 模糊比對：用編輯距離容忍打錯字。

對中文要特別注意：英文靠空白切詞，中文沒有空白，必須額外裝中文分詞器，否則搜尋效果會很差。

那為什麼不乾脆全部放進 Elasticsearch？ 因為它不適合當主資料庫：

  • 沒有關聯式資料庫那種跨多筆資料的交易，也不擅長 JOIN。
  • 寫入後不是立刻查得到，而是「近即時」，預設大約一秒後才出現在搜尋結果中。
  • 修改一筆資料實際上是整筆重建索引。

原文的說法，要打折看：原文說 Elasticsearch「比較不可靠、在大規模下較容易掉資料」「寫入慢很多」。前者在 2014、2015 年前後確實是有名的問題（當時有獨立測試證實在網路分割下會掉資料），之後的版本重寫了叢集協調機制，已經改善很多；後者過於籠統，批次寫入其實很快。不過結論不變：把它當成可以重建的副本，不要當成唯一的真相來源。

標準架構是兩個都用：

  • 新資料一律先寫進 SQL 主資料庫，它是唯一的真相來源。
  • 精確的查詢（我的商品列表、驗證密碼）讀 SQL。
  • 在背景把資料複製一份到搜尋引擎，搜尋框的查詢走搜尋引擎。
  • 搜尋引擎掉了幾筆資料，頂多是搜尋結果少了幾項，重新同步就好，不是災難。

怎麼把資料同步過去：

做法 說明 取捨
定時批次 每隔幾分鐘把有變動的資料撈出來寫過去 最簡單；有延遲
變更資料擷取（CDC） 讀資料庫的變更日誌，有變動就即時同步（例如 Debezium） 近即時；要多維運一套系統
應用程式雙寫 程式寫完 SQL 再寫搜尋引擎 看似最簡單，但不建議：第二步失敗時兩邊就不一致，而且很難察覺

原文提到 Craigslist 上架後顯示「15 分鐘內會出現在搜尋結果」，並推測背後是 SQL 加上 Elasticsearch 類的引擎。架構的推測方向是對的，延遲的成因則是原文作者的猜測。可以查到的是，Craigslist 用的搜尋引擎是 Sphinx，主資料存在 MySQL（依 2009 到 2012 年間的公開資料，現況未查證）。

補充兩點：

  • 不是一開始就需要搜尋引擎。MySQL 有 FULLTEXT 索引，PostgreSQL 有內建的全文搜尋和 pg_trgm 模糊比對。資料量不大、搜尋需求單純時，這些就夠用了，還省掉同步資料的麻煩。原文說 SQL 資料庫「不擅長全文搜尋」，更準確的說法是「內建的全文搜尋功能有限，到一定規模和需求後才需要專門的引擎」。
  • 2021 年 Elastic 更改授權條款後，AWS 另外分支出 OpenSearch。兩者概念相同，選型時會同時看到這兩個名字。

資料倉儲

要了解生意狀況，就得算全站的統計：每天各國各城市新增多少商品？每個月註冊的使用者有多少人在 90 天內上架過商品？

這種查詢不該對主資料庫跑，理由有兩個：

  • 會拖垮線上服務。分析師一個掃全表的大查詢，可以讓正式資料庫慢到使用者打不開網頁。
  • 主資料庫的設計本來就不適合。擅長「快速讀寫少數幾筆」的資料庫，處理「掃過幾億筆做加總」時會非常慢。

原文只講了現象，沒講原因。這其實是兩種完全不同的工作負載：

線上交易處理（OLTP） 線上分析處理（OLAP）
典型查詢 讀寫某一位使用者的幾筆資料 掃過幾億筆，做分組與加總
查詢量 每秒非常多，每個都很小 很少，但每個都很大
要求 毫秒級回應、資料即時 幾秒到幾分鐘可接受、資料晚一點沒關係
儲存方式 列式（row-oriented）：一筆資料的所有欄位存在一起 欄式（columnar）：同一個欄位的所有值存在一起
代表 MySQL、PostgreSQL BigQuery、Snowflake、Redshift、ClickHouse

關鍵在儲存方式。算「每天的銷售總額」只需要日期和金額兩個欄位。列式儲存得把每一筆資料的所有欄位都讀出來；欄式儲存只讀那兩欄，而且同一欄的值型別相同、重複度高，壓縮率很好。這就是資料倉儲快上幾十到幾百倍的原因。

**資料倉儲（data warehouse）**就是專門做這種大查詢的資料庫。資料每天（或更頻繁）從主資料庫複製過去，分析師在上面想怎麼查就怎麼查，不影響線上服務。

原文已過時的地方：原文用的是 Hive，並列出 Presto、Impala、Redshift 為替代方案。這是 2020 年、而且偏 Hadoop 生態的清單。現在新建資料倉儲很少選 Hive，主流是雲端託管的 BigQuery、Snowflake、Redshift，自架常見的是 ClickHouse，Presto 的主要分支在 2020 年底改名為 Trino。另外，Hive 嚴格說不是資料庫引擎，而是架在 Hadoop 檔案系統上的一層 SQL 查詢介面。

原文講的演進過程很真實，值得記住：創業第一年直接對正式資料庫跑分析，資料少所以沒事；直到某天一個大查詢把正式資料庫打掛，才去建資料倉儲。中間其實有個便宜的過渡方案原文沒提：先開一台專門給分析用的唯讀副本，就能隔離大查詢對線上的影響，等資料量真的大到副本也跑不動再上資料倉儲。

三個資料系統的分工

同一份資料存在三個地方，各自回答不同類型的問題：

系統 回答的問題 資料新鮮度
SQL 主資料庫 精確、小範圍、要最新最準的 即時，唯一的真相來源
搜尋引擎 模糊的文字搜尋、依相關性排序 落後幾秒到幾分鐘
資料倉儲 橫跨全部資料的統計分析 落後幾分鐘到一天

背景工作

Pub/Sub：事件發生後的連鎖動作

一個動作常會引發一串後續動作：新使用者註冊要寄歡迎信；新商品上架要通知訂閱了相關關鍵字的人，還要跑反詐欺檢查；商品賣出要發 webhook 給賣家。

這些後續動作技術上可以由處理請求的那台伺服器同步做完，但這樣不好。原文說「有兩個理由」卻只寫了一個，補齊如下：

  • 慢。「找出所有訂閱了電視通知的人並逐一通知」可能要好幾秒，使用者只是按了上架，沒理由等這個。
  • 耦合。寄信服務暫時故障，不該讓使用者的註冊跟著失敗。而且每加一個後續動作就得回頭改註冊的程式，註冊的程式會越來越肥，也越來越容易被不相干的改動弄壞。

**發布與訂閱（publish-subscribe，簡稱 pub/sub）**的做法：

  1. 動作發生時，程式發布一個事件，例如 NewListingCreated，內容是發生了什麼事。發布的程式到此為止，不需要知道誰關心這件事。
  2. 想在事件發生時做事的人寫一個消費者（consumer），訂閱這類事件。
  3. 中間由**訊息代理（message broker）**負責把事件交給所有訂閱者。
使用者註冊 ─> 應用伺服器 ─發布 NewUserSignup─> 訊息代理 ─┬─> 寄歡迎信的消費者
                                                         └─> 檢查垃圾帳號的消費者

事件怎麼到消費者手上有兩種方式：消費者主動去問代理（拉，Kafka 是這種），或代理主動送給消費者（推，例如對消費者發 HTTP 請求）。

好處：

  • 非必要的動作在背景做，使用者的操作保持流暢。
  • 程式乾淨：發布事件的一方不用管訂閱者做了什麼。要加新的後續動作，只要多寫一個消費者。
  • 消費者失敗了，系統可以記下來稍後重試。

常見的工具有 Kafka、RabbitMQ、AWS 的 SNS 與 SQS、Google Cloud Pub/Sub。附帶釐清一個容易混淆的概念：訊息佇列是一個訊息只給一個工作者處理（分攤工作量），pub/sub 是一個事件給所有訂閱者各一份（廣播）。很多工具兩種模式都支援。

原文把 pub/sub 講得只有好處，但它帶來的麻煩才是實作時的重點：

  • 事件可能重複送達。和 webhook 一樣，絕大多數系統提供的是至少一次的保證，所以每個消費者都必須是冪等的，否則使用者會收到兩封歡迎信，或被扣兩次款。
  • 事件可能不按順序到達。「商品已修改」可能比「商品已建立」先到。
  • 一直失敗的事件要有去處。重試幾次仍失敗的事件要移到死信佇列（dead letter queue），否則會卡住後面所有的事件。
  • 系統變成最終一致。註冊成功的那一瞬間，歡迎信還沒寄、垃圾帳號檢查還沒跑。大部分情況沒關係，但必須清楚哪些事可以晚一點、哪些不行。
  • 除錯變難。一件事的處理流程散在好幾個消費者裡，沒有一個地方能看到完整流程，需要靠追蹤 ID 把日誌串起來。
  • 「寫資料庫」和「發事件」不是一個原子動作。資料庫寫成功了、但發事件前程式掛了，後續動作就永遠不會發生。標準解法是 transactional outbox：在同一個資料庫交易裡，把事件也寫進一張 outbox 資料表，再由另一支程式把表裡的事件送到訊息代理。原文提到「簡單的系統可以把事件存在 SQL 資料表裡」，其實就是這個模式的雛形。

排程工作

很多事要在固定時間或固定間隔執行：每週寄用量報表、寄行銷信、對訂閱的使用者扣款、把資料從 SQL 複製到搜尋引擎。

最常見的工具是 Unix 內建的 cron。它普及到大家把所有排程工作都叫「cron job」，不管實際上是不是 cron 在跑。

用 crontab -e 編輯排程，每一行是五個時間欄位加一個指令：

*/5 * * * * /path/to/command

五個欄位依序是：分、時、日、月、星期幾。上面這行是每 5 分鐘執行一次。

最陽春的做法是準備一台專門的「排程伺服器」，把所有工作都放在它的 crontab 裡。原文點出兩個問題：這台機器掛了，你不知道哪些工作跑了、哪些沒跑；工作多到一台跑不完時也沒辦法擴充。

原文沒列、但寫排程工作一定會踩到的坑：

  • 重疊執行。每 5 分鐘跑一次的工作，某次跑了 7 分鐘，下一輪就會和上一輪同時執行。要加鎖（例如 flock），確保同時只有一份在跑。
  • 漏跑不會補。機器在排定的時間剛好關機或重開，cron 不會事後補跑。
  • 失敗時沒有人知道。cron 預設幾乎不告訴你工作失敗了。要有監控，而且要監控「該跑的有沒有跑」：讓工作每次成功後去打一個監控服務的網址，太久沒打就告警。
  • 時區與日光節約時間。排在凌晨 2:30 的工作，在切換日光節約時間的那天可能跑兩次或一次都不跑。伺服器一律用 UTC 可以避開。
  • 工作要寫成冪等。因為重試、補跑、手動重跑都會發生，「跑兩次」和「跑一次」的結果必須相同。扣款這類工作尤其重要：要先查這個帳期是否已經扣過。
  • 環境不同。cron 執行時的環境變數和你登入的終端機不一樣，手動能跑、排程卻失敗，多半是這個原因。

工作一多就會換成分散式的排程系統。原文提到 Kubernetes（它有 CronJob 這種資源），其他常見的還有 Airflow 這類工作流程排程器，適合工作之間有先後相依的情況。要注意 Kubernetes 的官方文件自己也說明：CronJob 在少數情況下可能執行兩次或漏掉一次，所以冪等的要求不會因為換了工具而消失。

內部管理工具

營運平台需要一堆自家專用的管理功能：下架違規商品、退款、客服查看使用者資料。使用者是公司裡的財務、法務、客服等部門，因為功能和自家業務綁得很緊，買不到現成的，只能自己做。

初期做法：直接做在主產品裡，資料庫有個 is_employee = True 的欄位，有這個標記的帳號就看得到管理功能。小公司這樣可以，但風險很明顯：

  • 最高權限和對外的產品跑在同一批伺服器上，主產品只要有一個安全漏洞，後果就會被放大成「攻擊者拿到管理權限」。
  • 容易出人為疏失，例如員工離職後忘了取消他的標記。

成熟後的做法：獨立的管理平台，跑在完全獨立、外界連不到的伺服器上，有另一套更嚴格的身分驗證與授權，要透過 VPN 加上用戶端憑證才進得去。它和主產品讀寫同一個資料庫，所以看到的是同樣的資料。

原文沒提、但內部工具的重點其實在這幾項：

  • 稽核日誌：誰、在什麼時候、對哪個使用者的資料、做了什麼，全部要記錄，而且不能被當事人修改。內部工具最大的風險不是外部駭客，而是內部人員的誤用與濫用。
  • 最小權限：不是每個員工都要能做所有事。客服能看訂單，但不該能改金額；用角色來劃分權限（RBAC）。
  • 敏感操作要雙人覆核：大額退款、刪除帳號這類動作，需要第二個人核准。
  • 預設遮蔽個資：電話、地址預設只顯示部分，要看完整的需要理由並留下紀錄。
  • 存取方式上，除了 VPN，現在也常見零信任的做法：不依賴「在內部網路裡就可信」，而是每個請求都驗證身分（公司的單一登入加上多因素驗證）和裝置狀態。

另外，原文說內部工具「直接連同一個資料庫」。這是可行的，但要留意：直接改資料庫會繞過主產品裡的商業邏輯（驗證規則、該發的事件、該清的快取）。比較穩的做法是讓內部工具呼叫主系統提供的內部 API，由同一套邏輯來處理。這一點是我的補充意見，不是原文的內容。

原文沒有涵蓋的部分

原文結尾列了「下次再談」的清單，這些也是完整拼圖的一部分，列在這裡當作之後學習的路線圖：

  • 安全：HTTPS 與加密、雙因素驗證、SAML（企業單一登入）、密鑰管理。
  • 伺服器管理：部署流程、雲端平台（AWS 等）、基礎設施即程式碼（Terraform）、負載平衡器、容器、監控與告警。
  • 大數據：MapReduce 類的批次運算、機器學習、使用者行為追蹤。

我認為還有三樣原文完全沒提、但同樣基本的東西：

  • 快取（Redis、Memcached）：通常是系統變慢時第一個該考慮的手段，遠早於分片。
  • CDN：把圖片、JavaScript 這類靜態檔案放到離使用者近的節點。
  • 負載平衡器：文中一直說「伺服器們」，把請求分給多台應用伺服器的就是它。它也是應用伺服器能夠水平擴充的前提：應用伺服器本身不保存狀態，狀態都放在資料庫和快取裡，所以隨時可以加減機器。
